# Persian review process

Status: **no native-speaker review has happened.** Every Persian string in Winora (Desktop, CLI, Worker) is a machine-assisted draft. The release statement says so, and nothing in the product may claim otherwise until a reviewer has signed off the status column described below. This document tells a reviewer what to do and tells maintainers how to take the result back into the `.resx` files.

## What is exported

`python a development tool that is not published (development tooling, read-only on the resx files) writes `technical-docs/persian-review.csv` from every `Strings.resx` / `Strings.fa.resx` pair in `src/Winora.Desktop`, `src/Winora.Cli` and `src/Winora.Worker`. UTF-8 with a byte-order mark so Excel and LibreOffice show Persian correctly. Regenerate it whenever strings change; reviewers always work from the newest file.

| Column | Meaning |
| --- | --- |
| host | Desktop, Cli or Worker (where the string is shown) |
| key | resource key. Never translate or rename a key. Keys that start `Code_` explain stable error codes; the code itself (for example `plan.stale`) is never translated. |
| english, persian | the two texts as they are now |
| flags | semicolon list: `machine-drafted` (all rows until reviewed), `missing-persian`, `missing-english`, `empty-persian`, `placeholder-mismatch`, `same-as-english`, `length-outlier` (Persian length under half or over twice the English, for English of 12+ characters), `latin-terms`, `digits-latin-adjacent` |
| placeholders_en, placeholders_fa | `{0}`-style placeholders found in each text. They must match as a set. |
| latin_terms | Latin-script runs left inside the Persian text |
| mixed_direction_risk | `none`, `medium` (a Latin word such as a product or file name inside Persian) or `high` (a path, extension, code-like token, or a digit touching Latin letters), where right-to-left reordering most often garbles the visible text |
| length_ratio | persian length divided by english length (informational) |
| review_status, reviewer_persian, reviewer_notes | filled by the reviewer |

At the time of writing the export has 907 rows (Desktop 647, Cli 210, Worker 50); one Desktop key (`FallbackProbe`) exists only in English on purpose, to test resource fallback. Counts are regenerated by the tool.

## Reviewer instructions

Work row by row. Set `review_status` to one of: `ok` (keep as is), `fixed` (you typed a better text in `reviewer_persian`), `question` (explain in `reviewer_notes`), `dont-translate` (technical token that should stay Latin). Leave `reviewer_persian` empty for `ok`.

Check each string for:

1. **Meaning and safety.** Winora tells people what will change on their computer. A wrong word can make a risky action sound safe. Be especially careful with: revert versus restore, applied versus pending restart, "needs sign-out", "external change", "conflict", "Explorer will restart and open folder windows will close". Read the English meaning in `english` and in the related `Code_*` rows.
2. **Natural register.** Polite neutral standard Persian (formal-neutral, not colloquial, not stiff bureaucratic). Second person addressed consistently. Buttons are short imperative or noun forms; messages are full sentences with a full stop (`.`), questions with `؟`.
3. **Terminology** against the glossary below. Propose a different term if you believe it is better and say why in `reviewer_notes`; maintainers then change every occurrence together.
4. **Placeholders.** `{0}`, `{1}` must stay, in a position that reads correctly in Persian. Do not translate the text inside braces. A `placeholder-mismatch` flag is always a bug.
5. **Digits.** The interface uses the culture's digits. Do not hand-convert digits that come from placeholders.
6. **Mixed direction.** For every `medium` or `high` row, imagine the string in the real window (right-to-left). Check that file names, extensions (`.txt`), paths and codes read in the correct order and that punctuation (parentheses, colon, full stop) does not jump to the wrong end. If it garbles, suggest rewording so the Latin token sits in the middle of the sentence or is quoted. Do not insert invisible direction marks yourself unless you are sure; say what you saw and maintainers will apply the isolating marks in the XAML.
7. **Length.** The window must still fit. A `length-outlier` flag is a prompt to check the string both for a possible omission (too short) and for a layout risk (too long). Buttons and navigation labels have the least room.
8. **Missing or identical text.** `same-as-english` is correct only for names (Winora in Latin, language endonyms) or technical tokens.

Please review in the running app where possible (the manual test plan, "Persian UI" section, lists the screens) because a string that is fine in a table can be wrong on a button.

## How to submit corrections

Either route is fine:

1. Fill `review_status`, `reviewer_persian` and `reviewer_notes` in a copy of `technical-docs/persian-review.csv`, save it as UTF-8, and send it to the maintainers (issue tracker location to be published by the owner). Do not reorder or delete rows.
2. Or edit `src/*/Resources/Strings.fa.resx` directly in a pull request, one commit per host, and say in the description that it is a native review. Do not change keys or English text in the same change.

Maintainers: apply `fixed` rows to the matching `Strings.fa.resx` files, keep a note of the reviewer and date in the commit message, rerun `python a development tool that is not published, and check that `placeholder-mismatch` is zero. `python a development tool that is not published checks resource parity and encoding. After applying, the Desktop tests that check key coverage in both languages and the manual Persian checklist (RTL, mixed direction, layout) must be rerun, because corrected text is often longer.

**Marking as reviewed.** A string counts as natively reviewed only when a named reviewer has covered the whole row set for that host and the corrections are merged. Until then the `machine-drafted` flag stays on every row and `release-limits.md` keeps saying so. The project has no mechanism yet to mark individual strings; if wanted, add a `<comment>reviewed:<name>:<date></comment>` to the data element and teach the export to read it.

## Known risks before review

Concatenated or formatted sentences (rows with `{0}`) may read awkwardly because word order differs; mixed-direction rows listed above; the Persian text of error-code explanations was drafted quickly and is the most safety-relevant to check; length-outlier rows; the single `same-as-english` row is the English language name label, which is intentional.
