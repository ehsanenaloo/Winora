# Compatibility

Foundation requires Windows with .NET 10 desktop runtime for WPF; SDK 10.0.401 is locally available. Candidate product support is Windows 11 x64/ARM64, with edition/build/hardware gates per feature. Windows 10 support is undecided because OS support and feature availability differ. No blanket Windows-version support claim. Services may be absent; policy settings may be edition-gated; GPU/CPU settings require vendor documentation and detection. 32/64-bit registry views and per-user/machine scope are explicit. Native ARM64, high DPI, older builds and alternate-credential UAC need disposable VM validation. Source conditions are evidence, not correctness proof.

## M1 read-only discovery adapters

Adapters live in src/Winora.Infrastructure.Windows and only read. Registry access uses KEY_READ (`OpenSubKey(path, false)`); no elevation is needed, and keys that need more become `access.denied` issues. Non-Windows hosts return `discovery.unavailable`. Registry views: HKLM is read in the 64-bit and WOW6432 views and kept distinct in ids; HKCU is read in the native view only. Startup: Run and RunOnce, Startup folders (.lnk/.exe/.cmd), StartupApproved flags (Run, Run32, StartupFolder). The StartupApproved byte encoding (first byte 0x02/0x06 enabled, 0x03/0x07 disabled) is observed shell behavior and not a published Microsoft contract, so unrecognised values are reported as Unknown; a missing record means enabled; RunOnce has no approval concept. Shortcut targets are read by parsing the documented Shell Link bytes (MS-SHLLINK), never through the shell. Tasks: Task Scheduler 2.0 COM (late-bound, no package); includes hidden tasks; tasks whose definition cannot be read are issues, not items. Services: configuration from HKLM\SYSTEM\CurrentControlSet\Services plus one read-only SCM enumeration (manager handle with enumerate right only); indirect "@file,-id" display names and descriptions are not resolved by the registry path (the SCM supplies the resolved display name, descriptions stay empty). Applications: Uninstall keys only; the uninstall command values are never read. Not covered: MSIX/AppX packages, per-user Appx registrations, Store apps, portable software without Uninstall registration, per-user services instances, ARM64 emulation specifics, and any non-default Windows edition behavior (untested on Windows 10, ARM64 or Server).

## M2 registry writer and shell refresh

Scope: HKCU only (64-bit view), 14 authored values, Windows 11 builds 22000 and later; per-entry MinBuild/MaxBuild (search.web_results ends at 22631; open_to, compact_view and search_mode start at 22621). Unknown build fails closed to unsupported. Windows 10, ARM64 native, Server and domain-policy-managed machines are untested; a machine policy (HKLM or HKCU\Software\Policies) can override a user value and Winora neither reads nor writes policy keys. Absent value equals the shipped default for several entries, so a fresh profile may show "no matching choice".

Shell refresh is a fixed pair of actions the product performs only after a confirmed apply. Broadcast: WM_SETTINGCHANGE to all top-level windows via SendMessageTimeout (SMTO_ABORTIFHUNG, 2 s each) with lParam null and "ImmersiveColorSet" only; no SHChangeNotify, no Environment/Policy strings because no catalog entry needs them. Restart Explorer: user-visible side effects are that open File Explorer windows close and the taskbar disappears and returns (flicker, a few seconds, tray icons reload). It posts the observed exit message to Shell_TrayWnd, waits up to 10 s for the user's own explorer.exe (%SystemRoot% image, same session and same user SID) to exit, lets Windows relaunch it (4 s), otherwise starts %SystemRoot%\explorer.exe with no arguments, and verifies Shell_TrayWnd returns within 15 s (one retry). Only if the graceful exit times out is that single matched process terminated (last resort). Failure returns shell.restart_failed; the registry change stays applied. Not tested against the real shell on any development machine; only fakes and the static source scan.

## M3 release packaging support statement

Applies to 0.x release artifacts only; it narrows, never widens, the statements above.

- **Supported target of the packaging:** 64-bit Windows 11, build 22000 or later, x64. The per-user MSI refuses anything else at install time (launch condition on `VersionNT64` and `WindowsBuild`), `Check-Prerequisites.ps1` reports the same, and the settings catalog fails closed on builds below each entry's minimum. Which builds actually work is only what the manual plan records for builds 22621, 22631 and 26100 once it has been run; 22000 (21H2) is allowed by the MSI and by 11 catalog entries but is not on the planned VM matrix, so treat it as untested.
- **Windows 10 (including 22H2, build 19045) is not supported** by these artifacts: not installable through the MSI, and the portable zip's apps are not tested there. The manual plan contains one expected-unsupported check to confirm the failure is clean. This settles the open Windows 10 question for the 0.x non-elevated tier only; it needs the owner's confirmation for later milestones.
- **ARM64 is not supported.** No ARM64 build exists; the zip ships only the win-x64 SQLite native, so an ARM64 machine running the x64 apps under emulation is untested and not claimed. Reconsider after a native ARM64 publish is tested on an ARM64 VM (ADR-008).
- **Runtime prerequisite:** .NET 10 Desktop Runtime (x64), framework-dependent. The MSI does not check for it; the app host reports it. Windows Server, N/KN editions and Windows Enterprise LTSC were not considered and are untested.
- **Per-user install, no elevation:** `%LOCALAPPDATA%\Programs\Winora`. The MSI cannot be installed per-machine in 0.x. Group Policy that blocks per-user MSI installs ("Disable Windows Installer", AppLocker or WDAC rules, Smart App Control) will stop the installer or the unsigned binaries; Winora does not try to work around any of them.
- **Locked-down machines:** a machine policy can override any of the 14 per-user values. Winora neither reads nor writes policy keys, so on such machines an apply can succeed in the journal and have no visible effect; the manual plan includes a check for this on a domain-joined VM if one is available (not required).
