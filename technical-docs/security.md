# Security and elevation protocol

## Current privilege model (implemented)

- The Desktop app requests administrator rights at start (manifest `requireAdministrator`) and refuses system changes when it runs from a folder that a normal user can write (location gating). It changes settings in its own elevated process, only through the closed catalogs and typed adapters; there is no generic write, command or script endpoint. The CLI stays unelevated and read-only for system scope.
- User-scope settings (HKCU) are written by the elevated Desktop process into the HKCU that its token sees. When the administrator account is not the signed-in user, that is the administrator's hive, not the user's. This is an open risk and has not been verified on the credential-switch case.
- Machine-scope changes use the same process. The separate worker (`Winora.Worker`) is still an inert executable: no handlers, every request is rejected with `worker.unimplemented`. The pipe protocol, trust checks and launcher of the sections below are built and tested against fakes; they are not the path that real changes take today.
- Journals of system changes are kept in an administrator-only folder (`C:\ProgramData\Winora\journals`). Startup and Permissions records are kept in one file per account (the SID is in the file name and in each record); older shared files are not loaded as undoable history. Journal records are untrusted data: undo re-reads the live state and restores only while the live value is still what Winora left.
- The unelevated launcher (`Winora.Launch`) and the single-instance pipe (see below) hand a page request to the running elevated app without a second consent prompt.
- Not verified: elevation under another account, Administrator protection, a second account on the test VM, Narrator and NVDA. See `verification.md`.

## Design for the elevation channel (partly implemented; not the current path)

The text below is the design of the privilege foundation. Where it says "future" or "Desktop is unelevated", it describes the target design, not the current model above.

Worker is an executable that rejects unsupported requests. Protocol v1 allows bounded typed commands with operation ID, trusted feature ID and desired typed value; never scripts, paths, registry targets or executable arguments. Unknown versions/features/commands are rejected. Maximum message 64 KiB, one operation per worker, 60 second idle timeout, cancellation only at safe boundaries.

IPC must use local-only pipes with explicit DACL for initiating SID and SYSTEM, reject remote clients, verify pipe client/server process token SID/session, authenticated nonce bound to parent PID/start time and request digest. Pipe name secrecy alone is insufficient. Worker independently resolves signed/versioned trusted definitions, authorizes scope and checks schema, limits, freshness and target identity. Profiles and journal records are untrusted data, not authorization. No generic remote execution.

Install worker in administrator-writable trusted location, verify signature/hash and path/reparse identity before UAC, account for TOCTOU; per-user writable deployment is insufficient for privilege trust. UAC with alternate credentials must not map HKCU to administrator: in the target design user-scope work stays in the initiating unelevated process and the machine worker rejects user-scope commands until explicit SID/token handling is reviewed.

Journal records must be appended by the trusted journal owner. Tampered journal cannot supply targets. Reject unknown/malformed versions and oversized data, validate desired values, protect nonce and avoid logging secrets. Recover by read-only discovery and definition validation. Signing, authenticated pipe implementation, ACL tests and credential-switch VM tests are release gates, not implemented claims.

## M2 registry writer

Registry mutation is confined to src/Winora.Infrastructure.Windows/RegistrySettingsAccess.cs. It exposes only Read, ReadRevision and CompareAndSet(definition, expected, desired). Every call re-validates that the definition is the catalog's own row (same id and version) with exactly the catalog's target; anything else throws target.not_allowed before any registry handle is opened. Targets are HKCU-relative, 64-bit view, with no rooted, dotted-parent or HKEY_/HKLM text (RegistryTargetRules, also enforced by the catalog self-check test). Reads open with KEY_QUERY_VALUE; writes with KEY_SET_VALUE (plus KEY_CREATE_SUB_KEY only when the key must be created). Absent deletes the single value and does nothing if the key is missing. A row can have several members (a group); the writer compares all members first, writes them one by one and puts the earlier ones back when a later write fails. A member can be a registry key (the classic context menu row): the writer creates it, and deletes it with DeleteSubKey only when it holds no subkey and nothing but what the row created (never a key tree, and never HKLM). Bit operations read the stored number first and refuse a missing or non-numeric value. Values are never environment-expanded, are limited to 64 KiB, and are written only after the live snapshot equals the caller's expected snapshot (best-effort compare-and-set; the registry has no atomic CAS, so a write landing between the re-read and the write is possible and is caught by the engine's post-write verification). Access denied maps to access.denied. The constructor accepts a non-default root only under HKCU\Software\WinoraTests\, used by tests; production passes none. A source scan test fails the build if any other file in the project calls a registry write, delete, process start or kill, or window-message API; ShellRefresh.cs is the single exception for the fixed shell actions (broadcast and graceful Explorer restart, documented in compatibility.md; and, pending owner approval, the pointer, keyboard repeat, accessibility keys, regional format and environment calls, which apply values the registry already holds), and it takes no path, command, number or process id from callers. SystemParametersInfo appears in that file only; a source scan enforces it.

## M3 local diagnostics (log and export)

Nothing leaves the machine: the log writer and exporter contain no network code, and the archive is a file in a folder the user names. The rolling log lives under `%LocalAppData%\Winora\logs` (UTF-8 JSON lines, 1 MiB x 5 files). Every message and structured state value passes `LogRedactor` before it is written: the user profile path (plain, slash, JSON-escaped and percent-encoded forms), any `X:\Users\<name>` path, UNC paths, the user and machine names, SIDs and e-mail addresses become fixed tokens. Exceptions are logged as type name, stable error code, inner types and `Type.Method` frames only; exception messages are never written. The exporter redacts again at export time, copies only identifier-shaped journal text (setting id, choice id, state, code, timestamps), never snapshots or registry data, and refuses UNC/device paths, network drives, a reparse-point destination, a linked ancestor that resolves into Winora's data folder, and the data folder itself. It never overwrites (next free name), writes to a temp name then moves, and caps the archive at 5 MiB and 24 entries. Redaction is best effort and the README tells the user to review before sharing. See [diagnostics.md](diagnostics.md).

The elevated app keeps the records it later acts on in `%ProgramData%\Winora\journals`. It creates that folder, and any missing folder above it such as `%ProgramData%\Winora`, with a protected ACL for SYSTEM and Administrators only. An existing folder is used only when it and every folder above it up to the drive root have a trusted owner and give no one else the right to delete, rename or re-permission it (the parent may still let users add entries); otherwise the records are not written and the change does not start.

At each start, before any record is read, the elevated app checks `%ProgramData%\Winora` itself. A folder that is missing is created admin-only. A folder that exists but is not admin-only (a user or a program made it first, or it is a link) is never used and never repaired in place: it is renamed to `Winora.untrusted-<UTC time>` in the same parent, so nothing in it is lost, a new admin-only folder is made, and the log says why. When a folder above it is not protected, nothing is moved or made, and the app stops with a plain reason text (English and Persian) that asks an administrator to fix the rights of that folder.

The operation journal (setting changes and their before and after values, machine rows, preferences) of an elevated app or command line lives in the same admin-only folder, one file per account: `%ProgramData%\Winora\journals\operations-<SID>.db`, so its rows always match the HKCU of the account that runs the app. A standard user cannot write it. The first start after an update copies the old `%LocalAppData%\Winora\simulation.db` once: it is copied into the protected folder and checked there, and only finished rows that read back as valid records, whose columns match the row and whose setting is in the catalog, are written into the new journal with their events; rows that are still active, quarantined or malformed are left out. The old file is then renamed to `simulation.db.untrusted-<UTC time>` and never read again, even when a new file with the old name appears. When the protected folder is refused, the app never falls back to the old file; it stops with the reason text. A process that is not elevated (the command line in a normal console) keeps using the file in `%LocalAppData%\Winora`, because it acts with the user's own rights; its changes do not show in the History of the elevated app.

Journals can be shared for support, so the paths they keep do not name the account: in the cleanup problem lines and in the program file of an uninstall record, the profile folder and any `X:\Users\<name>` path become `<home>`.


## Single instance and page hand-over (taskbar jump list)

Winora runs once per user and session. The Desktop app asks for administrator rights before any of its code runs (administrator manifest), so a taskbar jump list entry cannot start it without a consent prompt. The jump list therefore starts `Winora.Launch.exe`, a small program with the as-invoker manifest, no window and no dependency on the rest of the app. It hands the page to the open Winora over a local pipe and ends. When Winora is not open it starts the Desktop app, which shows the normal consent prompt once.

- Jump list: the page entries Overview, Customize, Cleanup, Startup, Apps and History, named in the language of the app. Each entry is `--page <key>` for the launcher. A key must be 1 to 32 ASCII letters; the app accepts only the keys of that fixed list. Any other key or argument is ignored and written to the local log. No entry changes a setting of Windows.
- Pipe: `Winora.Instance.v1.<session>.<hash of the user SID>`. The first Desktop process creates it as the first instance, one instance at a time. The access list is protected: network clients are denied and only the account that runs Winora can read and write. Nobody can create more instances of it. It has no integrity label, so a medium integrity launcher reaches an elevated app of the same account.
- Message: one length byte (1 to 64) and ASCII text `winora-nav-1:` followed by an optional page key. There is no other command and no data comes back except one answer byte (accepted, unknown key, malformed or too soon). The server reads under a 2 second limit, accepts one message per 300 milliseconds, and checks the session and the user of each client before it acts. A wrong length, text, user, session or key changes nothing.
- Window: an accepted message brings the window to the front and opens the page. While a dialog waits for an answer, the window only comes to the front. The sender gives the app the right to take the foreground, so Windows lets the window come forward.
- Other side: before it sends, the client checks that the process behind the pipe is the Winora Desktop program of the same install. A different process that took the pipe name first receives nothing and cannot stop Winora from starting; Winora then starts without the hand-over channel and writes a warning to the log.
- Elevation as another account: when a standard user starts Winora with the credentials of an administrator, the app runs as that administrator and has another pipe. The launcher of the standard user finds no app and starts a new one, which asks for the credentials and then hands over to the first instance. No page is handed across accounts.
- A start by hand (`Winora.Desktop.exe`) shows the consent prompt first, as Windows requires for the manifest; after consent it hands over to the open window and ends.
- Limits: the channel can only navigate to a listed page and bring the window forward. A program of the same account that reaches the pipe can do that and nothing else. Not verified: other Windows builds, other accounts, Narrator and NVDA announcing the jump list entries.
- Idle cost: the server waits with one asynchronous pipe operation. It has no timer and no thread of its own.

## Taskbar and notification area

Winora shows the progress of a long run on its taskbar button, two status badges ("A run failed", "Restart needed") and a notice when a long run ends while the window is not in front. It shows an icon in the notification area while the window is closed and a long run goes on. Everything comes from the activity service ([activity.md](activity.md)).

- Windows access: one reviewed file, `src/Winora.Desktop/Shell/ShellNative.cs`. It calls the taskbar list of the shell (progress, badge with a text for screen readers), `Shell_NotifyIcon` (icon, tool tip, notice), a native popup menu and the icon functions of user32 and gdi32. It starts no process, reads or writes no system setting and opens no channel to another process. No package was added for it.
- Messages from Explorer: Explorer runs without administrator rights. Windows blocks its window messages to an elevated window unless they are allowed one by one. Winora allows exactly three: the icon callback message of its own hidden notification window, "TaskbarCreated" (Explorer restarted, the icon is added again) and "TaskbarButtonCreated" (the taskbar button was made, progress and badge are sent again). A program of the same desktop that sends these messages can only open the window, open the menu, or make Winora draw its icon and progress again; the menu acts only on a choice made in the menu itself.
- The notice: a notice of the notification area icon (a balloon, which Windows 11 shows as a notification). A Windows toast for an unpackaged, elevated program would need an application identity, a shortcut in the Start menu and a COM activation server; Winora does not add those. The notice text is the run title and the page name; it holds no path and no value.
- Closing the window during a long run or a change: the window hides and the run goes on; Winora ends when the run is over. Exit in the icon menu asks first while a run goes, then asks every run to stop and ends when none is left. A change without Stop finishes first, so a change is never cut off by Exit.
- Setting "Keep in the notification area when the window closes" (off by default): with it on, closing the window only hides it, so the elevated Winora process keeps running until Exit is chosen in the icon menu. It does not start with Windows and adds no task, service or Run entry. While hidden and idle it has no timer of its own. A person who wants no elevated process left behind keeps the setting off.

## M4 design (privilege foundation; documents only, nothing implemented)

Written 2026-10-09 as phase 1 of M4 and revised the same day to apply the owner-delegated decisions D-01..D-22 (an unpublished design note, which override earlier documents) and the findings of an unpublished design note. The text above remains the standing contract and is left intact; where this section is more specific it SUPERSEDES the wording above, as listed next. There is still no pipe, UAC launch, signature check, definition verifier or machine-scope mutation in the repository, and nothing in this section may be cited as a security feature that exists. Details: [protocol.md](protocol.md) (SEC-001: channel, abuse cases, tests), [trust.md](trust.md) (SEC-002: install, signing, signed definitions, admission, state machine, audit), ADR-010..ADR-018 in [adrs.md](adrs.md), work packages in [m4-implementation-plan.md](m4-implementation-plan.md).

### Supersession of earlier wording

1. "Explicit DACL for initiating SID and SYSTEM" and "authenticated nonce bound to parent PID/start time and request digest" (paragraph 2 above) are superseded by protocol.md sections 5 to 8: the pipe DACL names the client's logon SID (no SYSTEM entry), the worker is authenticated by an attestation record, and keys come from a transcript-bound key exchange. Parent PID binding is dropped because process ids are spoofable or reusable (protocol.md 4.2). Pipe name secrecy alone is still insufficient.
2. "One operation per worker" means one batch of 1 to 8 operations per worker; "trusted feature ID" means a signed definition id plus version; "Protocol v1" in the earlier text names the foundation validator stub (`WorkerRequest`, `WorkerProtocol`), which is retired by work package A (D-16), not the wire protocol.
3. "Journal remains owned by the initiating user with restrictive ACL" is superseded for the profile folder: `%LOCALAPPDATA%\Winora` inherits the user's profile ACL and the design does not rely on it. The journal is untrusted evidence (R-30).
4. "Worker is an inert executable ... no UAC launch" remains true of the repository today. In phase 2 a production worker with an empty handler set rejects every request with `worker.unimplemented` before any definition lookup.

### Core decisions

1. Architecture (D-01, ADR-016): an on-demand UAC worker is the baseline, behind one transport seam (`IFrameChannel`) so a service transport could be added later under the promotion criteria in ADR-016. COM elevation and scheduled-task elevation are rejected.
2. The worker is launched with `ShellExecuteEx runas`; its manifest stays `asInvoker` (D-02). Because the launch crosses a UAC boundary no secret can be inherited or passed, so the command line carries only a public rendezvous id. The worker proves itself to the client with an attestation record that only an administrator-level process can write (Program Files `run\`) containing the hash of its ephemeral ECDH key; the client proves itself to the worker by kernel-reported identity (user SID, logon SID, session, Medium integrity) with PID/start time, install path and Authenticode as secondary evidence (D-04). The worker's first action is a token self-check; launched any other way it exits without creating an object.
3. An ephemeral P-256 key exchange bound to both identities, the protocol lists, the build flavor, the definition set hash and the batch digest yields per-direction AES-256-GCM keys with strict counters, 64 KiB frames, one connection and one batch. An independent cryptographic review is a gate before the first machine-scope definition; the fallback if it rejects the handshake is SSPI Negotiate with sign/seal. Honest limit: the channel cannot defend against code injected into the genuine client or against a same-user process that wins a race before the attestation check; UAC consent is the trust anchor.
4. The wire has a closed message set naming only a signed definition id and version, choice id, operation id and plan-token digest. The worker resolves targets from its embedded signed set (COSE_Sign1, ES256, pinned keys, verified before parsing; the signature layer arrives after M4a), is HKLM-only, and never touches HKCU, HKU or profile paths because the elevated account can differ from the initiating user (Administrator protection makes that normal).
5. Writes are two-phase so the initiating user's journal holds intent and the worker-observed before-state before Commit. Success is recorded only after the client's own read-back. Recovery is read-only, defers while a worker may still write, and never launches the worker (trust.md 11). The journal is evidence, never authority.
6. Elevation exists only for a signed per-machine installation (D-08). Portable, per-user and unsigned builds fail closed with typed codes. There is no runtime developer override; a compile-time `VmTrust` configuration exists for disposable VMs only (D-09).
7. The worker's trust boundary is a project boundary (ADR-015, D-03): it contains only `Winora.Elevation.Protocol` and `Winora.Elevation.Windows`, no DI container, no logging framework, no discovery, no shell refresh, no user-scope registry code. The worker is a Windows-subsystem program with no console and no log file (R-21, R-36).
8. Signing (D-07): SignPath Foundation first. The signer pin (subject, chain, key-hash set) identifies the signing service, not Winora; the worker's client check is the administrator-only install root AND the pin. The floor against definition replay is one registry value written only by the worker, effective against non-administrators only (D-06).
9. Machine-scope definitions are admitted only under the criteria of trust.md 7.1, with policy awareness (a policy-managed value is reported, never overridden), runtime reversibility (a value outside the restore domain is refused), no shell refresh, and two different reviewers (D-17). With one maintainer the machine tier stays closed and the release set stays empty.
10. Audit goes to the Windows Event Log (D-15, ADR-018) with redacted fields; it is best effort, forgeable by local writers, and never authority.

### Development-host guards (D-02, work package WP-0)

AGENTS.md forbids executing elevation code on the development host. The following is therefore required before any manifest, launcher or pipe code exists, in one change set: `tools/verify_dist.ps1` (the step that runs `Winora.Worker.exe` and asserts exit 3), a development tool that is not published (the `run(worker, exitcode=3)` call on `Winora.Worker.dll`) and `technical-docs/manual-test-plan.md` (step 5 and the U-29 row) stop executing the worker and read the PE (manifest level, subsystem, signature) instead. A guard test fails when any script under `tools/`, any test, any workflow under `.github/` or the manual plan executes `Worker.exe`/`Worker.dll`, with an allow-list only for the marker-guarded VM kit; no test project references the production worker project; the real launcher type is `internal sealed`, has no `InternalsVisibleTo` to tests and exactly one file may call `ShellExecuteEx`. The VM kit refuses to run without `WINORA_VM_TESTS=1` and the VM marker file.

### Test inputs and the machine path (R-24, R-25)

Inventory of test and developer inputs today: `--sandbox-root <name>` (hidden; redirects registry access to `HKCU\Software\WinoraTests\<name>` and swaps in a no-op shell refresh), `--database PATH`, `--no-log`, `WINORA_NO_LOG`, `WINORA_DATA_DIR`. `tools/verify_dist.ps1` uses them against the shipped CLI, so they cannot simply be compiled out; the guarantee is structural plus fail-closed at runtime.

1. Machine-scope commands live in a distinct CLI verb (`machine ...`) and a distinct application service (`IMachineSettingsExecutor`) whose construction takes no path, root, database, logger-disable or shell-refresh parameter. Its composition obtains paths only from the LocalAppData known folder and the install record; it never reads `WINORA_*` variables and never accepts the options above.
2. Fail closed on presence: when any of those variables is set, or any of those options appears on a `machine` command, the command exits 2 before reading state with `elevation.unavailable` (detail `testhook`) and a localized message. A hook is neither silently honored nor silently ignored on a machine path. The Desktop host treats the variables as inert and logs one startup line.
3. No shared fakes in shipped assemblies: the no-op shell refresh stays internal to the CLI and is not registered by the machine composition (machine scope performs no shell refresh); a published-assembly scan lists every type whose name contains `Fake`, `Sandbox` or `Test` and compares it with an allow-list.
4. Machine journal rows use only the default data root, which must be on a fixed local volume and not a reparse point.
5. The machine registry target class has no sandbox-root parameter, no HKCU member and a compile-time constant hive of HKLM; the existing HKCU `RegistrySettingsAccess` is not used by the machine path; a source scan keeps the two apart.
6. The worker reads no environment variable and nothing named `WINORA_*`; its only inputs are the strictly parsed option set of protocol.md 4.4 (exact set, each once, bounded, ASCII). An unknown option, a duplicate, a response file (`@file`) or an environment-supplied option exits with the argument-error code before creating any object. The test-only inputs are not compiled into, and are ignored by, every machine-scope or elevated code path (the AGENTS.md exception text of ADR-015, pending owner application).
7. VM-only affordances (self-test definitions, the VM marker check, the test root importer) are compiled only under `WINORA_VM_TRUST` and removed from release by the scan in trust.md 5. No runtime switch enables them.
8. Tests: U-A04 (machine composition refuses with each hook present), U-A05 (machine namespaces do not reference the CLI log setup, data-path overrides, the no-op refresh or the HKCU access class), U-A06 (published assemblies: type-name allow-list), U-L04 (worker option parser rejects `@file`, duplicates, environment sources), U-W17 (scan of the worker's referenced code).

### Logging and privacy of the privileged side (R-36)

The worker writes no file log and uses no stdout/stderr; its diagnostics are the early-failure record and, optionally, fixed-token ETW. The client logs through the existing redactor (which also learns the install-root path pattern and the distinction between the initiating and the elevated account). Journal v4 columns (transcript hash, worker-observed before-state digest, worker identity including any SID) are excluded from the diagnostics exporter and a test proves the export of a v4 database contains none of them nor any SID (U-L05). Event Log fields follow trust.md 12.3.

### Release gates

Concrete form of the earlier statement: the unelevated test tiers in protocol.md section 16 passing; the dev-host guards green; all V-tier tests passing on a disposable VM on two builds including V-09 (environment injection) and V-14 (credential switch); signing authority chosen and used only in protected CI. Milestone M4a (the full channel with one harmless typed no-op, D-14) precedes journal v4, definitions and the installer. The gate before the FIRST real machine-scope definition ships is trust.md 13.4: external review of the channel, all VM experiments passed or fallbacks adopted, the definition-signature layer, the per-definition checklist, policy awareness, and the two-reviewer rule.

### Open risks (M4 design)

1. Unverified OS behaviors (marked `[U]` in protocol.md and trust.md) can change the design; none was tested. M4a exists to settle the channel-related ones.
2. Same-user code injected into the genuine client, and a same-user process that wins a race before the attestation check, are out of scope; the closed definition set and UAC consent are the only bound.
3. The SignPath grant, pins and renewal behavior are unknown; until they are, elevation stays disabled everywhere. The signing subject identifies the service, not the project.
4. Offline operation: no CA revocation, definition revocation only by release (D-10); the floor defends against non-administrator replay only (D-06).
5. Worker runtime: NativeAOT feasibility (S0) and the environment-hook behavior (V-09) are unproven; the self-contained fallback detects but cannot prevent pre-`Main` hooks.
6. Dev-host safety depends on the WP-0 guard change set landing first.
7. One maintainer cannot meet the two-reviewer rule; the machine tier stays closed until a second reviewer exists.
8. Event Log audit entries are forgeable by local writers of the Application log; they are an audit trail, not tamper-evident evidence.
