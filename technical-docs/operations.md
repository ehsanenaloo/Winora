# Operation contract

Lifecycle: Discover -> compatibility -> Plan -> Preview -> Prepared (before-state + intent committed) -> Executing (committed) -> mutation -> actual-state verification -> committed outcome. Preparation failure forbids mutation. Cancellation is honored before preparation and between steps, never halfway through a mutation; reconcile after an uncertain result.

States: Planned, Prepared, Executing, Applied, AlreadyConfigured, Unsupported, Failed, Partial, PendingRestart, Reverted. Planned -> Prepared/Unsupported/AlreadyConfigured; Prepared -> Executing/Failed; Executing -> Applied/Failed/Partial/PendingRestart; Applied/PendingRestart -> Reverted/Partial on compensation. Recovery may resolve Prepared/Executing to Applied (actual equals desired), Failed (actual equals before), Partial (neither). Terminal outcomes are not guessed.

Snapshots preserve type and presence. Registry state must distinguish missing key/value from present null-like data, value type and 32/64-bit view. Feature/operation identifiers are stable independent of translated labels. Intent contains schema/definition version and resource identity. Unknown future schemas fail closed. Migration is transactional and versioned; journal IDs and before-state never become profile data.

Apply is idempotent by reading actual state. Multi-step changes are not atomic: compensate in reverse order only when current state equals the recorded applied state, otherwise classify external conflict. Undo is reversible, conditional or irreversible per definition; never universal. Before compensation persist its intent. On crash reconcile actual resource and journal; do not replay untrusted journal targets. Retry only after reconciliation.

Simulation storage is durable local SQLite state, not Windows state. Single-step simulation tests failure-before-mutation, interruption after mutation, idempotency and external-change rollback. The production engine's multi-step execution, resource leases across processes, profile execution, reboot and Explorer refresh are future work and unavailable.
## Simulator implementation (M0 hardening, FND-002 reduced scope)

Implemented on the SQLite simulator only; no Windows state is read or written.

- Schema v2 (PRAGMA user_version=2). v1 -> v2 migration is one BEGIN IMMEDIATE transaction (rename, rebuild with real columns, ledger seed, drop, version bump); any failure rolls back and leaves the v1 file intact. A v1 file missing `operations` or `simulated_resource` fails closed (journal.schema_corrupt); a missing `preferences` table is recreated; unparseable v1 rows are migrated into quarantine; more than one active v1 row fails the migration (journal.migration_conflict). Foreign v0 databases and future versions are rejected; a v2 file missing required tables/indexes/triggers is rejected.
- Every write path (prepare, save, compare-and-swap, quarantine, preferences, initialization) is BEGIN IMMEDIATE. SQLITE_BUSY/LOCKED surface as StoreException `store.busy`; other SQLite failures as `store.failure`. The wait is the Microsoft.Data.Sqlite per-command timeout (5 seconds in production), not a PRAGMA.
- `operations` has real `rev`, `state`, `compensation_prepared`, `resource_id`, `quarantined` columns. A partial unique index on `resource_id` (not quarantined, state Prepared/Executing or compensation prepared) enforces one active operation in the database. `Save` is `UPDATE ... WHERE id AND rev`; a lost race throws `journal.revision_conflict`. Identity and intent fields are immutable after prepare.
- `op_events` is an insert-only ledger (triggers abort UPDATE/DELETE), written in the same transaction as every transition and validated against the transition table in `OperationTransitions` (Application): Planned -> Prepared/Unsupported/AlreadyConfigured; Prepared -> Executing/Failed/Applied/Partial; Executing -> Applied/Failed/Partial/PendingRestart; Applied/PendingRestart -> same with compensation prepared or Partial; compensation prepared -> same state (abandoned), Reverted or Partial. Terminal states have no exits.
- The simulated resource carries a `revision` bumped by every write. Mutation is a compare-and-swap on value and revision and is additionally bound to the journal row revision, so a concurrent recovery that already ruled on the row prevents the mutation. Change-away-and-back (ABA) loses the CAS: Apply records Failed with `operation.external_conflict` (not Partial) and may be retried.
- Prepare is one store transaction: active check, read of actual state and revision, optional plan-token check, insert. `Plan` returns a token (current, revision, desired); `Apply(desired, token)` fails with `plan.stale` if anything moved. Apply without a token keeps the old behavior.
- Recover: Prepared/Executing resolve from actual value plus revision (unchanged -> Failed, source revision + 1 and desired -> Applied, otherwise Partial); interrupted compensation returns to Applied (`operation.rollback_abandoned`) when the resource is untouched, to Reverted when the compensation write is visible, otherwise Partial. A verdict commits only if the resource is unchanged since it was read. Rows whose payload is untrusted (unparseable, future schema, wrong definition, columns disagreeing with payload) are quarantined with a ledger event instead of blocking other work.
- Rollback is bound to the resource revision the operation produced (`AppliedRevision`). A newer Winora operation makes an older rollback refuse with `operation.superseded` (record unchanged); an external change classifies Partial/`operation.external_conflict`; a second rollback of a Reverted record returns it unchanged; a concurrent rollback that loses the revision-guarded save returns the winner's record. The compensation intent and the resource check commit atomically.
- Persistence faults are handled uniformly: the engine catches StoreException/IOException/InvalidOperationException around the mutation and reconciles from actual state; cancellation after preparation records Failed `operation.cancelled`.
- Error handling: see technical-docs/errors.md.

Residual limits (unverified or deliberately absent): no real Windows resource, lease, reboot or Explorer refresh; no multi-step operations; PendingRestart is never produced; v1 records migrated without revisions cannot be rolled back (`operation.revision_unknown`) and reconcile on value only; the single-resource assumption is baked into the unique index (resource_id) but only one resource exists; durability depends on SQLite FULL synchronous and the host file system (no power-loss test); rollback-journal mode only (WAL untested); multi-process evidence is four local processes on one machine; synchronous calls can block up to the busy timeout.
## M2 settings engine (registry settings, schema v3)

Implemented in `SettingsService` (Application) over `ISettingOperationStore` (SqliteOperationStore, Persistence) and the `IRegistrySettingsAccess` / `IShellRefresh` ports. Verified only against in-memory and file-backed fakes; the real adapter and shell are other components' evidence.

- Journal: tables `setting_operations` and `setting_events` (insert-only ledger, triggers abort UPDATE/DELETE) added by a transactional v2 -> v3 migration (v1 files migrate v1 -> v2 -> v3 in one transaction). A partial unique index allows one active row per setting; in addition `PrepareSetting` and any save that makes a row active again (compensation prepared) refuse with `operation.recovery_required` while ANY setting operation is active (global rule).
- A row holds ids, definition version, a target fingerprint, the choice id and typed before/after snapshots (key/value presence, view, kind, raw bytes). It never holds a write target: every write goes through `IRegistrySettingsAccess.CompareAndSet(definition, expected, desired)` with the definition re-resolved from the catalog by setting id. A row whose setting is unknown, whose definition version or target fingerprint differs, whose choice is unknown, or whose snapshot view/kind is not one the definition can produce is untrusted: recovery quarantines it (`journal.untrusted_definition`, `journal.invalid`, `journal.schema_unsupported`), revert refuses it, and no registry write happens.
- Grouped rows (DEC-IW-034): a catalog row can have several members. The snapshot of a row then holds one entry per member (the first entry carries the others in `More`; rows written before this change have one entry and stay valid), the target fingerprint names every member, a choice sets all members in one compare-and-set, and a state where only some members match a choice has no matching choice (shown as a custom value). Undo restores every member with its exact earlier kind and bytes, or removes it again, and only while all members still equal what Winora wrote. A bit operation (clear or set bits of a number that is stored as a DWORD or as a decimal string) is refused with `setting.state_unrecognized` when the number is missing or not a plain number; undo restores the exact earlier number, not a recomputed one. A key member is created, and deleted again only while it holds nothing but what Winora created.
- Plan: validates id, choice and build (unknown build fails closed for build-bounded settings), reads the snapshot (it must read the same twice), and returns a token over id, version, choice and snapshot. The key last-write time is recorded in the journal for diagnostics only; no decision compares it (ADR-019). A value whose kind the definition cannot restore is refused with `setting.state_unrecognized`.
- Apply: recompute and compare the token (`plan.stale`), `AlreadyConfigured` without a registry write, `Prepared` (before-state and intent committed) -> `Executing` -> compare-and-set with expected = observed snapshot (a value-level check; the key last-write time is not compared) -> re-read -> verify. A lost CAS is `Failed` + `operation.external_conflict`, never `Partial`.
- Shell refresh (owner-approved fixed actions only, through `IShellRefresh`): after a verified write the row is committed as `PendingRestart` with `operation.refresh_pending` (intent), then the fixed apply actions the definition names (pointer, keyboard repeat, accessibility keys, "intl" or "Environment" broadcast; owner approval pending), the general broadcast and, when the definition requires it and options allow, the Explorer restart run, then the outcome is committed: `Applied` (`operation.shell_refreshed`) only if every required action succeeded; otherwise `PendingRestart` with `shell.refresh_failed`, `shell.restart_failed`, `operation.cancelled`, `operation.restart_pending` or `operation.signout_pending`. Sign-out definitions stay `PendingRestart`. `CompleteAsync` re-runs the refresh (journaled, a no-op on Applied; for sign-out definitions it changes nothing because it cannot be verified). Revert refreshes the same way; a reverted row whose refresh did not complete stays `Reverted` with a pending/failure code and can be completed. Transitions added for this: PendingRestart -> Applied, PendingRestart -> PendingRestart, Reverted -> Reverted.
- Revert restores the recorded before snapshot only if the live snapshot equals the recorded after snapshot (the key last-write time is not compared, so a rewrite of the same value does not block it); absent before-value reverts by deleting the value, a present value restores kind and bytes. Otherwise `Partial` + `operation.external_conflict` (or `operation.superseded` when a newer Winora operation changed the setting) and no write.
- Recover reads the actual registry through the catalog target (never journal targets): Prepared/Executing resolve to Failed (equals before), Applied (equals desired; a Prepared row whose value matches desired is Partial because the mutation never started) or Partial; compensation rows resolve to abandoned, Reverted or Partial. Rows interrupted during a refresh only re-run the idempotent broadcast; recovery never restarts Explorer. A row whose owner process (pid + start time) is still alive is left alone.
- Cancellation is honored before prepare, between prepare and executing, and before the compensation intent; never after the mutation starts. Blocking store and registry calls run on the thread pool; faults surface as `WinoraException` with catalog codes, cancellation as `OperationCanceledException`.

## M4 machine rows (journal schema v4)

Machine-scope changes use their own tables, `machine_operations` and `machine_events`, in the same database. The state machine, the durable boundaries and the recovery verdicts are specified in [trust.md](trust.md) section 11; this section records what the store enforces.

- Schema v4 adds the two tables, a partial unique index (one active row per definition) and immutable ledger triggers. A new database is created at v4. A v3 database is first copied with the SQLite backup API to a temp file and then moved, without overwriting, to `<name>.v3.bak` in the same folder (one backup per source version); a failed copy stops the migration. The migration runs in one transaction: any failure leaves the v3 file as it was.
- One active row of any kind: a row is active in `Prepared`, `Executing` or with the compensation flag. A new machine row is refused while any setting or machine row is active, and a user row is refused while a machine row is active (`operation.recovery_required`). The same check applies when a row becomes active again through a revert.
- A machine row is created at `Prepared`. Allowed moves: `Prepared` to `Executing`, `Failed`, `AlreadyConfigured` or `Partial`; `Executing` to `Applied`, `PendingRestart`, `Failed` or `Partial`; `Applied`, `PendingRestart` and `AlreadyConfigured` to `Partial` (drift); the revert path `Applied` or `PendingRestart` to the same state with the compensation-prepared flag, then with the compensation-committed flag, then to `Reverted` or `Partial`, or back to the applied state when the revert is abandoned. The committed flag never exists without the prepared flag (also a CHECK constraint).
- Immutable after the first write: definition id and version, set serial and hash, batch digest, plan token, choice, the before snapshot and its key revision, the schema version, the creation time and the restart flag. The worker-observed before snapshot, once set, never changes.
- Payload rules: digests are 64 lowercase hex characters, snapshots are canonical hex that re-encodes to the same bytes, unknown fields and a wrong schema version make the row untrusted. An untrusted row is listed for recovery and can be quarantined; a quarantine writes a ledger event and lifts the block without any machine action.
- The executor (`MachineSettingsExecutor`) is the only writer. It journals each boundary before the step it guards, decides outcomes from its own unelevated read-back, and treats a worker that may be alive as a reason to wait (worker lock probe, or the boot session recorded in the row). It handles one operation per batch in this milestone; a batch of two or more is refused.

## Unconfirmed records (every journal of a setting change)

A record with a begin line and no end line is unconfirmed. The journal order for a change is begin, written, end: the written line is appended after the native write returned and before the end line. It is kept for machine settings, power plans, permissions, startup entries, services, scheduled tasks and DNS. At start the app closes an unconfirmed record only when the outcome is proven: the record has a written line and the live state is the intended one (Applied, undo stays a compare-and-set), or the live state is still the one from before (Failed). A state equal to the intended one without a written line does not show who set it, so the record stays open and gets no undo. A crash between the write and the written line leaves the record unconfirmed.

The History page offers two ways to close an unconfirmed record, each after one confirmation. Keep the current value: nothing is written and the record is closed as Dismissed (no undo). Put the earlier value back: an ordinary change that goes through the usual preview checks, has its own record (not marked as an undo) and its own undo, and is written only while the value is still the one that was just read; the unconfirmed record is then Dismissed. Neither choice makes the old record an owned, undoable change. Setting types that cannot be put back (a service start or stop, a task run or delete, a plan copy) offer Keep only. A DNS undo is offered only for a change that is Applied or Partial.

Preinstalled apps: an unconfirmed removal or reinstall record can only be dismissed. Winora does not guess whether the app was removed.
