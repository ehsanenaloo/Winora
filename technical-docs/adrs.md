# Architecture decision records

## ADR-001 — Layered hosts and adapters

Accepted, foundation. Context: both WPF and CLI need one engine, while privilege and persistence must remain outside domain rules. Decision: seven requested boundaries; Application references Domain only, adapters reference these layers, hosts compose them. Consequence: no SQLite/WPF/Windows dependency in neutral layers; no extra framework or empty product-feature classes. Windows adapter currently exposes read-only platform discovery only.

## ADR-002 — Durable local SQLite simulation

Accepted, foundation. Context: a journal commit must precede each mutation, but Windows resources cannot participate in a shared database transaction. Decision: explicit FULL synchronous SQLite transactions for initial schema, preparation, execution marker, simulated resource and outcome. One pending simulated resource reservation is checked inside the preparation transaction; actual state uses compare-and-exchange. Consequence: outcome persistence failure leaves recoverable intent; actual-state reconciliation is mandatory. Single boolean simulation is intentionally bounded; multi-resource event history, revisions/ABA detection and multi-process orchestration remain FND-002. No power-loss durability beyond filesystem/device guarantees is promised.

## ADR-003 — Inert worker until authorization is complete

Accepted, foundation. Context: a generic elevated execution channel would expand the attack surface before trusted definitions exist. Decision: typed v1 request DTO and fail-closed validator; inert asInvoker executable, no listener or UAC request. Future short-lived elevation requires authenticated local-only pipes and trusted installation/signature decisions. Consequence: real privileged functionality unavailable until SEC-001/002; user-scope remains with initiating user, especially under alternate credentials.

## ADR-004 — Observable resource localization

Accepted, foundation. Context: Persian needs live RTL changes and stable untranslated operation identity. Decision: English neutral .resx, Persian satellite, observable indexer bindings, culture and flow-direction updates, SQLite preferences, LTR technical fields. Consequence: stored codes stay independent of labels; no app restart for language choice. Screen-reader, high-contrast and DPI manual verification remain FND-003.

## ADR-005 — Dependency locks and reproducible prerequisites

Accepted, foundation. Context: .NET 10 and UI packages must be available and compatible. Decision: global.json SDK 10.0.401, central exact package versions and NuGet locks; Windows CI restore in locked mode. Consequence: initial network restore is expected; runtime stays offline; actual SDK/package compatibility is evidenced by local builds, not assumed APIs. Git history is not initialized without a user request.

## ADR-006 — Bounded synchronous simulation calls

Accepted for foundation only. Context: a single local SQLite boolean operation has no remote/Windows call or long-running step. Decision: synchronous Application port, cancellation at initial safe boundary, no invented asynchronous backend. Consequence: a contended database may block up to the configured five-second busy timeout. Production multi-step scheduling and responsive background UI execution need a reviewed task before real integrations.

## Open decisions

Windows 10 support and supported editions/builds; trusted installer location and signing; specific official/vendor settings permitted; privileged journal ownership validation; multi-step lease/revision semantics; quarantine size/retention UX; hardware measurement protocol; ARM64/native dependency packaging. These questions do not authorize fallback behavior or claims of compatibility.

ADR-017 (M0; formerly the second ADR-006, see the numbering note below): Accepted. Context: foundation journal had latest-state rows, deferred transactions and value-only compare. Decision: schema v2 with BEGIN IMMEDIATE on all writes, row and resource revisions, real state columns with a partial unique index, an insert-only ledger validated by a transition table, atomic prepare with plan tokens, quarantine of untrusted rows, recovery verdicts bound to the resource read, and a unified error catalog (errors.md). Consequences: older operations cannot undo newer ones; migrated v1 rows lose rollback; the synchronous design and single simulated resource remain; WAL, power-loss durability and Windows leases are unverified.

ADR-007 (M2 engine): Accepted. Context: real registry settings need the M0 invariants without trusting the journal as a source of write targets. Decision: separate setting journal tables in schema v3; rows carry ids and typed snapshots only, the target is always re-resolved from the catalog and fingerprint-checked; compare-and-set with expected = observed snapshot plus a best-effort key revision hint; global single-active rule on top of the per-setting unique index; shell refresh journaled as its own transitions and Applied only after verified success; recovery reconciles from actual state and skips rows whose owner process is alive; blocking calls run on the thread pool. Consequences: registry ABA detection depends on key last-write time (coarse: any value written in the same key moves it, so external writes can cause conservative conflicts but never an overwrite); there is no atomic registry CAS, so a live writer racing a recovering process is handled by owner-liveness, not atomicity; a value of an unmanaged kind is never overwritten.

## ADR-008 (M3): Packaging, installer and runtime model

Accepted for 0.x on 2026-10-09; owner decisions are listed at the end. Context: the M3 release candidate is the non-elevated tier (HKCU only). It must be installable without administrator rights, removable without surprises, verifiable offline, and must not close doors for the M4/M5 elevated worker (technical-docs/security.md: the worker must live in an administrator-writable trusted location, be signature-checked and launched through UAC).

Decision.

1. **Unpackaged, not MSIX.** Winora ships as an ordinary Win32 .NET application: a portable zip plus a per-user MSI. MSIX is rejected for now because (a) the later elevated worker, HKLM and service work needs real machine registry and service access, and MSIX package identity, file-system and registry virtualization would sit between the product and the very resources it manages (the exact "virtualization surprise" a settings manager cannot afford: an HKCU write that lands in a package-private hive would look successful and change nothing); (b) MSIX requires a signing certificate trusted on the target machine to install at all, so unsigned test builds could not be installed, whereas an unsigned MSI/zip can at least be tried with a SmartScreen warning; (c) the Explorer restart and sign-out actions and the discovery adapters assume an unvirtualized process. Revisit only if a Store channel becomes a goal and the runtime behavior is re-verified inside a package.
2. **Per-user MSI built with WiX Toolset SDK 5.0.2 plus a portable zip.** The MSI installs to `%LOCALAPPDATA%\Programs\Winora` with a Start menu shortcut and the normal Apps & features entry (per-user, so no elevation), uses a fixed UpgradeCode with a major-upgrade rule (newer replaces older, downgrade blocked), has no custom actions, services, PATH or file associations, and never touches `%LOCALAPPDATA%\Winora` (user data is kept by default; removal is a documented manual step). The WiX SDK is restored from NuGet like any package (nothing is installed globally; the exact version is pinned in the .wixproj Sdk attribute and its lock file is committed); its license is MS-RL (nuspec license URL https://licenses.nuget.org/MS-RL). WiX is used only at build time and contributes no code to the artifacts (verified by the absence of a CustomAction table), so the MS-RL copyleft does not attach to a GPL-3.0-only distribution; this is the project's reading, not legal advice. ICE validation is switched off on the build host because it opens Windows Installer; it must be run on a VM. The MSI is built and inspected read-only here and has never been installed or run by the project.
3. **Framework-dependent, win-x64.** Measured on this machine (SDK 10.0.401, runtime 10.0.12), all three applications published and merged:

| Variant | Uncompressed | Zip |
| --- | --- | --- |
| Framework-dependent, only the win-x64 SQLite native kept (shipped) | 14.6 MB (66 files, three app folders) | 6.5 MB (MSI 3.9 MB) |
| Framework-dependent, unpruned (SQLite natives for every platform) | about 78 MB for the three apps | not measured |
| Framework-dependent + ReadyToRun (experiment, merged layout) | 13.2 MB vs 10.8 MB without | 5.7 MB vs 4.6 MB |
| Self-contained win-x64 (experiment, merged layout) | 154.8 MB, 428 files | 68.7 MB |

A self-contained build is about 15 times larger to download, duplicates the runtime that Windows Update-style servicing keeps patched when it is shared, and was therefore not chosen for 0.x. The cost is a prerequisite: the .NET 10 Desktop Runtime (x64) must be installed. Mitigations: the app hosts show Microsoft's missing-runtime message, `Check-Prerequisites.ps1` (read-only) is shipped, and the release notes say so. The MSI does not block on the runtime because the runtime registers per version value names that an MSI search cannot wildcard; the limitation is accepted and recorded. If the owner prefers self-contained, the change is: set a RuntimeIdentifier and `SelfContained` for the three projects, regenerate the lock files (a RID adds a lock target), and expect the sizes above.
4. **Not single-file.** Single-file framework-dependent WPF would need native-library extraction for SQLite and WPF's native components, hides what is shipped from inspection and checksum review, and complicates the per-file hash list. Three app folders (`desktop`, `cli`, `worker`) are shipped exactly as `dotnet publish` emits them, because the apps resolve different target-framework variants of the same package (SQLitePCLRaw.provider.e_sqlite3 differs between Desktop and CLI) and cannot safely share one folder.
5. **No trimming.** Trimming is unsupported for WPF applications, and the other apps use reflection-heavy libraries (dependency injection, SQLite provider, resource lookup). PublishTrimmed is therefore not used and must not be added. **ReadyToRun** is not used in 0.x: it needs a RuntimeIdentifier restore (invalidating the committed lock files), pulls the crossgen pack, adds about 22 percent to the uncompressed size, and the startup benefit measured here (median of five runs of `Winora.Cli.exe --version`: about 330 ms without, 260 ms with) is within the noise of a laptop that also ran other agents' builds. Re-measure on a quiet VM before reconsidering.
6. **x64 only; ARM64 is explicitly unsupported** until built natively and run on an ARM64 VM (technical-docs/compatibility.md). The MSI launch condition and `Check-Prerequisites.ps1` refuse ARM64 and anything older than Windows 11 build 22000.
7. **Where it lives.** Per-user: `%LOCALAPPDATA%\Programs\Winora` (MSI) or any folder (zip). Per-machine (`Program Files\Winora`) is deliberately deferred.

M4 consequence (per-machine install). technical-docs/security.md requires the elevated worker to be installed in a location that ordinary user code cannot modify, checked by signature and hash before UAC. A per-user directory is writable by the user and by any process running as the user, so it cannot be a trust root. M4 will therefore need: a per-machine package (ALLUSERS, `Program Files\Winora`, one UAC prompt at install), a signed worker and signed desktop, installer-registered worker identity that the Desktop verifies before every launch, and a decision whether the Desktop stays per-user while only the worker moves. Winora's data stays in `%LOCALAPPDATA%\Winora` either way. Moving existing 0.x users from the per-user to the per-machine package is not designed and not tested: expect "uninstall the per-user package first" until a VM test shows a safe in-place upgrade path with the same UpgradeCode. Nothing in 0.x may claim otherwise.

Consequences. Unsigned artifacts trigger SmartScreen and may be blocked by Smart App Control; this is stated in RELEASE-LIMITS.md. The framework-dependent choice means correctness depends on the installed runtime version (the lock files fix package versions, not the machine's runtime). The ReadyToRun and trimming decisions can change without a format change.

Owner decisions needed: code-signing certificate and who holds it; publisher/manufacturer name (the MSI says "Winora project" as a placeholder); whether to ship self-contained; update channel (none in 0.x); the issue tracker and security contact addresses.

## ADR-009 (M3): Reproducible, checksummed and unsigned release artifacts

Accepted 2026-10-09. Context: users cannot rely on a signature yet, so the project must at least make the artifacts verifiable and rebuildable. Decision: `tools/publish.ps1` builds with `ContinuousIntegrationBuild`, maps the checkout path away (`PathMap`), forces a fresh compile without debug symbols for the shipped assemblies, stages files with a fixed timestamp, writes the zip in ordinal name order with a fixed entry time, and emits `SHA256SUMS`, `FILES.sha256` (inside the zip), a CycloneDX-style package list (authored in the repository from `dotnet list package` output and nuspec files, no tool download) and a release-notes stub. `-ReproCheck` builds again from a copy of the tree at a different path and compares. Result recorded in verification.md: the zip, SBOM and every staged file were byte-identical; the MSI differs by a few dozen bytes because WiX 5 writes a new package code and timestamps on each build and has no switch to pin them, so the MSI is checksummed but not claimed reproducible. Signing is not performed anywhere; the CI file documents where it would be added. Consequence: any later signing step changes file bytes, so the zip, hashes and MSI are produced after signing, and verify_dist.ps1 must switch from "must be unsigned" to "must be signed by the expected publisher".

The first keeps ADR-006 (technical-docs/architecture.md refers to it by that number). The M0 journal-hardening record is renumbered ADR-017 and stays in its original position above (its heading says so). A search of the repository found no document that cites the M0 record by number, so no reference needed rewriting; if one is found later it means ADR-017. ADR-007 to ADR-009 are unchanged. New numbers: ADR-015 (worker project graph), ADR-016 (elevation architecture), ADR-018 (audit trail). ADR-010 to ADR-014 are the M4 privilege-foundation decisions (design only, Proposed, pending owner approval; nothing is implemented); they were amended on 2026-10-09 to apply the owner-delegated decisions D-01..D-22 in an unpublished design note, which override the earlier text where they differ.

## ADR-010 (M4): Elevation channel, handshake and two-phase operations

Proposed 2026-10-09; amended 2026-10-09 (D-04, D-02, D-14, D-16). Full text: [protocol.md](protocol.md). Context: `ShellExecute runas` starts the worker in a different logon context (and for a standard user a different account), so handle inheritance fails and any secret in the command line or environment must be assumed visible to same-user code. Decision: the unelevated client launches the signed worker (runas); the worker creates a single-instance, first-instance, remote-rejecting pipe with an explicit DACL for the client's logon SID and publishes an attestation record in the administrator-only `<InstallRoot>\run` directory containing the hash of its ephemeral ECDH key; the client sends nothing until the pipe server key matches the attestation; the worker authenticates the client from kernel-reported pipe identity (user SID, logon SID, session, Medium integrity) with the client image path and Authenticode signature, and PID plus start time, as SECONDARY evidence only, and keeps listening through up to three failed identity checks; session keys come from ephemeral P-256 ECDH and HKDF-SHA256 over a transcript that binds both identities, nonces, protocol version lists, the build flavor, the definition set hash and the batch digest; frames are AES-256-GCM with direction-separated keys and 96-bit counter nonces, a 64 KiB cap, one connection, one batch (max 8 operations) per worker; writes are two-phase (Prepare returns the worker-observed before-state, the client journals it durably and marks Executing, then Commit); the client always re-reads live state before recording Applied. No X25519, Ed25519 or ChaCha20-Poly1305 in the baseline. The channel specification must contain every encoding (protocol.md Appendix A) before any code. An independent cryptographic review is a gate before the first machine-scope definition ships (trust.md 13.4); if it rejects the custom handshake the fallback is SSPI Negotiate with sign/seal over the pipe, keeping the attestation file for server authentication. First milestone M4a carries one harmless typed no-op through this channel (D-14). The foundation `WorkerRequest` stub and `WorkerProtocol` are retired with the first work package (D-16). Alternatives rejected: inherited handles or environment secrets (cannot cross UAC), shared secret on the command line (public), TLS over the pipe (large elevated parser surface), persistent elevated service or scheduled task (ADR-016), COM elevation moniker (ADR-016), trusting the pipe-owner PID or image signature alone (a same-user attacker can run the genuine image unelevated), a single-phase "apply and report" command (cannot meet persist-before-mutate). Consequences: client authentication is by OS-reported identity, so injection into the genuine client and a same-user process that wins a race before the attestation check are out of scope and bounded only by the closed definition set and UAC consent; several OS behaviors are unverified and gated by VM experiments; the worker needs write access to Program Files `run\`.

## ADR-011 (M4): Trust root, per-machine install and signing policy

Proposed 2026-10-09; amended 2026-10-09 (D-06..D-10, D-12, D-13); amends the M4 consequence of ADR-008. Full text: [trust.md](trust.md) sections 2 to 5 and 13. Decision: elevation exists only for a signed per-machine installation under Program Files; the portable zip, the per-user MSI and unsigned or unpinned builds report a typed unavailable code and never raise UAC; a per-machine MSI ships only together with the elevated worker (D-08). The per-machine package has a NEW UpgradeCode (instead of the in-place upgrade with the same code that ADR-008 left open); the per-user line is frozen; migration is "uninstall the per-user package, then install", data untouched. The per-machine MSI does not author or own the anti-rollback `Trust` key (the worker creates it, D-06); it authors only the non-permanent `HKLM\SOFTWARE\Winora\Install` values and the Event Log source rows. Desktop, CLI and worker all live in the trusted root because the worker authenticates its client by path and signature. Signing (D-07): SHA-256 Authenticode with an RFC 3161 timestamp, CI-only protected signing environment; apply to the SignPath Foundation now, with an OV certificate on a cloud HSM or Azure Artifact Signing as fallbacks. The signer is pinned by certificate subject plus trusted-root chain plus a small set of issuing-key hashes, never a single thumbprint. Because the SignPath subject is shared by other projects, the worker's client check is the administrator-only install root AND the subject pin; the subject identifies the signing service, not Winora, and with a shared-subject service the signature check is a tamper check, not a project identity. A signed release manifest is reserved for the case that the install-root control proves insufficient. Risks accepted explicitly: the Foundation can pause the subscription or revoke the certificate. Runtime developer overrides (environment, registry, file, flag) are rejected (D-09); a compile-time `VmTrust` configuration with separate identities (folder `WinoraVm`, registry `WinoraVm`, pipe prefix, flavor byte, UpgradeCode) and keys is accepted for disposable VMs only and is scanned out of release artifacts. Elevate-without-consent configurations are allowed with an in-app warning plus a second confirmation; the non-interactive CLI refuses (D-12). Platform stance (D-13): Windows 11 24H2 primary, 22621 and 22631 tested, Administrator protection and Smart App Control handled as typed codes until a VM run settles them. Alternatives rejected: elevation from the portable package, leaf-thumbprint pinning, online revocation checks in the offline worker, a "developer mode" setting, relying on a WiX `Permanent` component for the floor. Consequences: users without admin rights never get machine settings; online revocation does not exist; the signing grant is a blocking prerequisite for release; MSI Manufacturer and the UAC-displayed publisher differ.

## ADR-012 (M4): Signed definitions embedded, with a monotonic floor

Proposed 2026-10-09; amended 2026-10-09 (D-05, D-06, D-10, D-14, D-18). Full text: [trust.md](trust.md) section 6. Decision: the machine definition set is a restricted-profile UTF-8 JSON payload signed byte-exactly as a COSE_Sign1 with detached payload, ES256 (ECDSA P-256), two or three pinned public keys, verified BEFORE parsing, embedded as resources (the worker holds its own copy; Desktop and CLI hold another; skew is detected by the set hash). No JSON canonicalization, which removes the parser-differential class at the signature boundary. The definition-signature layer is NOT part of M4a; the release set stays empty and the VmTrust no-op is built in. The set hash is bound into the attestation and handshake transcript. Freshness is a monotonic `serial` compared with a floor stored as ONE `REG_BINARY` value in an administrator-ACL'd key `HKLM\SOFTWARE\Winora\Trust` created by the worker; the MSI never owns it. The floor protects against replay by non-administrators only: administrators can reset it and a restored backup restores the old floor. Definitions carry `restoreCompatible` (versions whose rows they can restore); a revoked definition without `allowRestore` refuses restore with a typed code (D-18). Revocation is a `revoked` list in a newer set and takes effect only through a new release (D-10); that lag is a documented limit to be revisited before the first machine-scope definition. Alternatives rejected: file in Program Files (TOCTOU and version skew), CBOR payload, canonical JSON, Ed25519 (no supported path found), ML-DSA (not a baseline), time-based expiry, floor in ProgramData or the user profile, two separate floor values, TPM counters (not shown practical). Consequences: a COSE package enters the elevated image (to be pinned, noticed and proven under the chosen runtime in spike S0); the definition/Authenticode separation is a process control; M4 ships an empty release set so the feature stays disabled until M5 adds reviewed definitions.

## ADR-013 (M4): Machine-scope authorization, admission rules and journal ownership

Proposed 2026-10-09; amended 2026-10-09 (D-15, D-17, D-18, D-19). Full text: [protocol.md](protocol.md) sections 11 and 12 (message and authorization rules), [trust.md](trust.md) sections 7 and 11 (admission, state machine, recovery). Decision: the wire carries only definition id and version, choice id, operation id and plan-token digest (a restore value only inside the definition's restore domain, and shown to the user before it is written); the worker resolves targets solely from the verified set, is machine-scope and HKLM-only, and has no code path to HKCU, HKU, profile folders or environment expansion because after UAC its token user may be a different account; the initiating SID comes from the pipe token and is audit data, not authorization. The initiating user's unelevated process owns the journal (schema v4 adds scope, set serial and hash, batch digest, transcript hash and worker-observed before-state digest; receipts only if protocol.md keeps them, R-29 recommends removing them), journals intent before Commit, creates rows one at a time, and verifies by its own read-back; recovery is read-only, defers while a worker may still write and never launches the worker. The journal is evidence, never authority. Admission rules (documented Microsoft source, reversible and restorable at run time, no deletion, one bounded target, readable without elevation, no protection downgrade, policy respect via `managedBy`, no shell refresh, two-person review, VM evidence) gate every machine definition. Approver model (D-17): no definition ships until two different people have reviewed it; with one maintainer the machine-scope tier stays closed and the release set stays empty. Audit goes to the Event Log (ADR-018), not to an HKLM record. The M2 HKCU path receives the same flush/drift verification and policy awareness as a separate task before M5 (D-19). Alternatives rejected: a worker-owned journal (SQLite in the elevated TCB, wrong account under alternate credentials), per-user work in the worker, accepting arbitrary restore bytes from the journal, generic registry targets in requests, an HKLM audit key. Consequences: recovery requires definitions readable without elevation; a stale Executing row can remain unresolved until a worker-gone proof and read access are available, with a user-initiated review action as the way out; a definition version bump without `restoreCompatible` makes earlier applied rows unrevertable.

## ADR-014 (M4): Worker runtime model and hardening

Proposed 2026-10-09; amended 2026-10-09 (D-02, D-03, D-11). Full text: [protocol.md](protocol.md) section 14. Decision: the worker is a minimal-dependency Windows-subsystem program (no console, hidden launch, no stdout/stderr) built from Winora.Elevation.Protocol and Winora.Elevation.Windows only (ADR-015: no SQLite, no DI container, no logging framework, no WPF). Its manifest requests `asInvoker`. Elevation is obtained only by the client's `ShellExecuteEx` `runas` launch, which elevates an `asInvoker` image; the worker's first action is a token self-check (elevated, High integrity) and otherwise it exits 3 without creating any object, so an accidental double-click or script launch is harmless. The `requireAdministrator` manifest is rejected because it would raise UAC whenever a script, test or IDE launches the image on a development machine (R-01). Rule: no build, test, script, CI step or documented procedure may execute the worker image on the development host; only the marker-guarded VM kit may, and a source scan enforces it. Runtime: run spike S0 for NativeAOT with the Windows subsystem; if NativeAOT works, ship it; if not, ship self-contained with startup-hook support disabled in the runtime configuration AND an exit with a typed code when any `DOTNET_*`, `COMPlus_*`, `COR_*` or `CORECLR_*` hook, profiler or startup-hook variable is present. Limit of that fallback: the environment check runs inside `Main`, after startup hooks and profilers would already have loaded, so it detects but does not prevent; prevention in the self-contained case rests on the disabled startup-hook support, and release is blocked until experiment V-09/X1 proves the chosen model. The worker hardens at start (DLL search restriction, process mitigation policies from a committed required/optional table, a job object with process, memory and handle limits, no child processes, no Process APIs; source and assembly scans enforce it). ADR-008's no-trimming and framework-dependent decisions remain true for Desktop and CLI. Consequences: `tools/verify_dist.ps1`, a development tool that is not published and `technical-docs/manual-test-plan.md` step 5 stop executing the worker and inspect the PE (manifest level, subsystem, signature) instead, in one change set that lands before any manifest or launcher code (plan WP-0); NativeAOT adds ILCompiler and runtime packs to the central package list, lock files, notices and SBOM; release is blocked until V-09 passes for the chosen model.

## ADR-015 (M4): Elevated worker project graph (amends ADR-001)

Proposed 2026-10-09 (D-03). Context: referencing Winora.Infrastructure.Windows from the worker would put discovery, the user-scope registry writer and the Explorer restart (process termination) into the elevated process, and the planned protocol library inside Winora.Application would link all of Application into it (R-02). Decision: two new minimal projects. `Winora.Elevation.Protocol` is pure and references Domain only: framing, handshake, codecs, the session state machines over an `IFrameChannel` seam, rollback policy and, later, the definition verifier. `Winora.Elevation.Windows` holds the Windows primitives: pipe server and client, token and identity checks, image guard, SDDL, mitigations, the HKLM target and the launcher. The Worker executable references only these two (plus Domain transitively), is a composition root without a DI container or logging framework, and contains only `Main` and hand-written composition; the testable session loop therefore lives in Protocol and needs no separate Worker.Core project. Application keeps referencing Domain only: the orchestrator in Application depends on ports declared in Application/Domain, and the client-side implementation of those ports (channel use, launcher) lives in an Infrastructure.Windows adapter that references Protocol and Elevation.Windows. This amends ADR-001 by adding the two projects and the rule that adapters may reference them; the Application sentence is unchanged. Open point for the owner: the launcher (`ShellExecuteEx`) is in Elevation.Windows by D-03, so it would be linked into the worker's assembly graph although the worker never launches anything; either the assembly scan allows an `internal` launcher that NativeAOT trims (not provable for the self-contained fallback) or the launcher moves to the client adapter. The recommendation is to move it. Exception text to be applied to AGENTS.md when phase 2 starts (STATUS: PENDING owner application; not applied):

"The elevated worker executable is a composition root without a DI container or logging framework, referencing only Winora.Elevation.Protocol and Winora.Elevation.Windows. It registers an empty handler set in production and rejects every request with `worker.unimplemented`. Test-only inputs (--sandbox-root, --database, WINORA_DATA_DIR, WINORA_NO_LOG) are not compiled into, and are ignored by, every machine-scope or elevated code path."

Consequences: the project-reference graph and the published worker's referenced namespaces are enforced by tests (the Worker's transitive closure equals an allow-list; no `System.Diagnostics.Process`, `Microsoft.Extensions.*`, `Microsoft.Data.Sqlite` or `Winora.Infrastructure.*`); a non-shipped test worker project (`asInvoker`, test-only handlers, refuses to run under Program Files) exercises the session loop unelevated; the real launcher is `internal sealed` with no `InternalsVisibleTo` to tests and exactly one file may call `ShellExecuteEx`; the worker plan item O-8's earlier default (reference Infrastructure.Windows) is withdrawn.

## ADR-016 (M4): Elevation architecture: on-demand UAC worker with a transport seam

Proposed 2026-10-09 (D-01). Context: machine-scope changes need administrator rights; Winora is an offline, GPL, asInvoker desktop application. Evidence: an unpublished design note. Decision: option A, an on-demand UAC worker launched with `runas`, is the baseline. The operation core is built around one transport seam (`IFrameChannel`) so a service transport can be added later without redoing definitions, plan tokens, journal or two-phase operation. Rationale: a resident service that changes machine settings without a prompt turns any same-user malware into a machine-settings writer; option A confines each elevated session to a user-approved prompt and leaves no resident privileged code. Rejected options and reasons: (B) per-machine service reachable by every local user: permanent local-privilege-escalation surface, per-call authorization of non-elevated callers is the hard part, highest maintenance, a security-servicing obligation; (C) elevated COM local server via the elevation moniker: the UAC prompt still appears, needs HKLM class registration and per-interface marshaling, conflicts with NativeAOT and trimming, so more moving parts for the same prompt; (D) scheduled-task elevation: an on-demand highest-privilege task can be started without a prompt, a known standing escalation surface, with no safe parameter channel; (E) hybrid service limited to an allow-list of operations safe for a standard user: the right long-term shape only if demand and a reviewed allow-list exist, so deferred. Promotion criteria for the service option (E, then possibly B): (a) at least one managed-fleet customer requires prompt-free changes; or VM experiments V-03, V-06 or V-09 fail in a way the fallbacks cannot absorb; (b) a reviewed allow-list exists of operations whose worst case is acceptable if invoked by any local user; (c) capacity exists for a security-servicing process; (d) token-based per-call authorization is designed (never PID-based), with a service DACL that denies non-admins change-config and stop rights. Evidence that would change the decision: V-03 shows a Medium client cannot query the elevated worker at all and the attestation cannot be made robust; V-09 shows the worker honors caller environment variables even under NativeAOT; V-06 or V-19 show `runas` unusable under Administrator protection or with UAC off (then option A is unavailable on those configurations and the product refuses explicitly). Confidence: high for rejecting C and D; medium-high for A over B. Consequences: prompt fatigue is the main UX cost (each batch asks again); standard users without administrator credentials cannot use machine settings; the first milestone M4a proves the channel end to end with a typed no-op before journal v4, definitions or the installer change (D-14).

## ADR-018 (M4): Audit trail in the Windows Event Log

Proposed 2026-10-09 (D-15). Full text: [trust.md](trust.md) section 12. Decision: the elevated worker and the unelevated client write a redacted audit trail to the Application event log under a dedicated source named `Winora`, with stable event ids (client 1000-1099, worker 2000-2099). Fields are operation id, definition id and version, choice id, mode, outcome code, set serial and short hashes, and a hashed caller SID; never paths, values the user typed, restore or snapshot bytes, nonces, keys or the transcript hash. The source is registered by MSI registry rows only (no custom action). Writes are best effort and never change an outcome; the log is never read back and never authority. Alternatives rejected: an HKLM audit record (an unneeded machine-writable store, R-27's proposal), a worker-owned file log (filesystem state in the elevated process). Consequences: enterprises can collect the entries with what they already use; entries are forgeable by any local writer of the Application log, so they are an audit trail, not tamper-evident evidence; a custom event channel with a restrictive ACL is a possible later step if tamper evidence becomes a requirement.

## ADR-019: The value is the witness of state for user-scope settings

Accepted 2026-10-11. Context: the settings engine compared the registry key's last-write time (a "revision") besides the value to detect outside changes. On a real Windows 11 machine (build 26200, one VM) Explorer writes to shared keys such as the Search key when it starts, which moves the last-write time without changing the value. A revert after an Explorer restart was then refused as an outside change and left the setting changed. A key timestamp cannot say which value was written, and the registry has no atomic compare-and-set, so it did not close the race it was meant to narrow.

Decision. For user-scope settings the observed state is the typed snapshot (key and value presence, view, kind, raw bytes), read twice and required to be equal. The plan token commits to the setting, definition version, choice and snapshot. Apply and revert use the value-level compare-and-set of the registry adapter and refuse when the live snapshot differs from the expected one. The key last-write time is still read and stored in the journal for diagnostics. It is never compared. A change away and back to the identical value is therefore not treated as an outside change: restoring the recorded before-state is the user's intent and does not lose any information.

Scope. This covers the user-scope settings service only. The simulation engine (its own versioned resource) and the machine-scope protocol (technical-docs/protocol.md) keep their revision rules until that design is reviewed; their references to a revision are unchanged.

Consequences. A rewrite of the same value by Windows no longer blocks a revert or invalidates a plan. A different value still does. Tests in the engine suite pin both directions. The design in ADR-007 and operations.md is amended accordingly. Not verified: other builds and other writers of shared keys.

## ADR-020: A presentation layer without UI types between the rules and the window

Accepted 2026-10-23 (owner decision of 2026-10-20: the UI layer keeps only the look). Context: the view models lived in the WPF project and used WPF and WPF-UI types (brushes, colors, font symbols, control appearances, visibility, flow direction). Page state could not be tested without the UI framework, and logic could drift into the window.

Decision. A new project `Winora.Presentation` holds the page state and commands (view models), the text service and the search model. Dependencies point one way: `Winora.Domain` and `Winora.Application` (rules) are referenced by `Winora.Presentation`, which is referenced by `Winora.Desktop`. `Winora.Presentation` also references the portable part of `Winora.Infrastructure.Persistence` (the operation store and data paths, no Windows API). It has no reference to WPF, WPF-UI or a Windows-only target framework, so a UI type in a view model does not build. `Winora.Application` and `Winora.Domain` never reference `Winora.Desktop` or WPF.

What lives where. The view models expose meaning only: a tone (neutral, info, success, caution, danger) or a risk, severity, state or kind enum, an icon key (the name of a pictogram), a text direction, and plain booleans for visibility. `Winora.Desktop` maps meaning to look in shared converters, styles and controls (tone to badge, icon key to font symbol, text direction to flow direction). Things a view model needs from the shell (UI-thread dispatch, dialogs, clipboard, file and folder pickers, launching the Store and Windows Settings, signing out, loading application icons) are interfaces declared next to the view models; the implementations are in `Winora.Desktop`, and tests use fakes. Code-behind keeps layout, focus and dialogs; anything that decides, computes or reads the system sits in Presentation or Application and has tests there.

Enforcement. Architecture tests in `Winora.Guards.Tests` fail when a source in the presentation layer names `System.Windows`, `Wpf.Ui` or `PresentationFramework`, when the project file references WPF or a Windows-only target, and when `Winora.Application` or `Winora.Domain` references the Desktop project or WPF. Namespaces of the moved files stay `Winora.Desktop` to keep the change small.

Consequences. View model tests can run without a window. The screenshot baselines are the proof that moving the code did not change the look. The Desktop assembly and the installer layout gain one more assembly, `Winora.Presentation.dll`.

Open decisions added by M4 are tracked in [m4-implementation-plan.md](m4-implementation-plan.md) section 8, where each is marked DECIDED (with its D-number) or OPEN (with a recommendation).
