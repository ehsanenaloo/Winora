# Architecture and decisions

Domain owns value records, state transitions, typed snapshots, resource identities, desired profiles, uninstall ownership and versioned worker messages. Application owns planning, simulation orchestration, recovery and ports. No WPF, SQLite or Windows APIs enter these layers.

Persistence implements Application ports with Microsoft.Data.Sqlite, schema version checks and FULL synchronous commits. The Windows adapter holds discovery and the reviewed native mutation adapters (registry, services, scheduled tasks, power, DNS, packages, uninstall launcher, quarantine). Desktop (WPF + WPF-UI + CommunityToolkit.Mvvm), CLI and Worker each compose through Microsoft.Extensions.DependencyInjection and logging. Desktop and CLI share the same simulation engine. The Desktop app requires administrator rights and runs the native adapters in its own process; the Worker (elevation protocol) is built and tested, registers an empty handler set in production and rejects every request.

ADR-001: retain seven requested boundaries; no general framework or separate protocol assembly. ADR-002: SQLite owns durable journal and simulated resource, each preparation/outcome transition in explicit transactions; a Windows mutation will never share its atomicity. ADR-003: short-lived UAC worker is future, fail closed until authenticated typed protocol is complete. ADR-004: resource-backed shell uses observable localization, per-control LTR islands and persisted preferences; no copied third-party UI. ADR-005: pin .NET 10 and package versions, commit NuGet locks, no Git initialization without a human request.

Planning requires explicit compatibility, dependencies, resource overlap and risk. Simulated single-step boolean setting is the only trusted executable feature. Production settings remain backlog entries, not successful stubs. Shared resources require canonical identity and ancestor/descendant overlap, not label comparison.

Detailed decision context and consequences: [ADRs](adrs.md). Primary mechanism evidence: [source register](sources.md). Foundation uses synchronous bounded local calls (ADR-006); real integrations require separately reviewed scheduling. No persistent background worker is implemented.

Error handling: a single stable catalog (Domain ErrorCode/ErrorCatalog/WinoraError), one exception mapper and reporter port in Application, hosts localize by resource key; see [errors.md](errors.md). Persistence journal is schema v2 with revisions, an insert-only transition ledger and quarantine; see operations.md.

M2 settings engine: `SettingsService` (Application) implements `ISettingsService` over `ISettingCatalog`, `IRegistrySettingsAccess`, `IShellRefresh`, `IOsBuildProvider` and `ISettingOperationStore`; `SqliteOperationStore` (Persistence, schema v3) implements the store port next to the M0 `IOperationStore` and shares its connection, transaction and fault-hook plumbing. Setting rows live in separate tables so M0 simulation rows and setting rows never mix. Domain holds `SettingOperationRecord`, snapshot helpers and plan tokens. See operations.md (M2 settings engine).

M3 diagnostics: `FileLoggerProvider` (a Microsoft.Extensions.Logging provider), `LogRedactor`/`RedactionContext`, `AppDataPaths` and `DiagnosticsExporter : IDiagnosticsExporter` live in Persistence next to the journal (it already owns the application data folder and reads both journal ports). Hosts wire them at the composition root: the CLI in `CliLog`/`Program.cs`; Desktop registers the provider itself and calls `IDiagnosticsExporter`. Application keeps only the fixed `IDiagnosticsExporter` contract. See [diagnostics.md](diagnostics.md).

Layers of the desktop app (ADR-020): `Winora.Presentation` holds the view models, the text service with the resx files, the search model and the shell view model. It references Domain, Application and the portable part of Persistence, and has no WPF or Windows-only reference. `Winora.Desktop` references it and keeps XAML, styles, controls, converters from meaning types to look, windows and the Windows implementations of the shell services. `Winora.Application` and `Winora.Domain` never reference Desktop or WPF. Architecture tests enforce these rules (`Winora.Guards.Tests`). The namespace of the moved code stays `Winora.Desktop`.

Single instance: `Winora.Instance` is a small library with no reference to any other Winora project (the page key list, one message format, a named pipe server and client). `Winora.Desktop` references it for the running instance and the jump list. `Winora.Launch` is a second executable with the as-invoker manifest that references only `Winora.Instance`; it starts or reaches the Desktop app without asking for administrator rights itself. Neither project touches settings, the journal or the elevation channel. Security notes: [security.md](security.md) "Single instance and page hand-over".
