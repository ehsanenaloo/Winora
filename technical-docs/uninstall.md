# Uninstall and leftovers policy

Contracts only: discover MSI product code, registered Win32 uninstall metadata and MSIX/AppX package identity, user/machine scope and registry view. Invoke official uninstaller only in a future separately reviewed adapter; record cancellation, failure, restart and unknown outcome. Re-discover before candidate scan; never infer ownership from name similarity.

Candidate evidence records exact installation/package identity, manifest/install log provenance, location, publisher, resource identity, confidence and reasons. Shared runtimes, publisher-wide directories and shared registry keys are preserved by default. User documents/projects/application data require a separate explicit selection; low confidence is never selected by default. Reviewed selections and evidence are not blanket deletion authorization.

Before cleanup revalidate canonical path, identity, type, size/hash or registry snapshot, lock/permissions and concurrent changes. Never follow reparse points, junctions or symlinks; no recursive escape. Services/tasks/shortcuts/startup entries need executable/package linkage and shared ownership checks. Preserve registry value type and view in backup. Locked files and pending reboot remain explicit outcomes.

Proposed quarantine: local same-volume move when safe, 512 MiB per operation/2 GiB total, 30 days retention, explicit retention review, no auto deletion in foundation. Over-limit targets require separate irreversible review. Restore verifies destination conflicts and never overwrites newer data; restored leftovers do not reinstall the application. These limits are design defaults pending disk/UX testing. The leftover flow (below) uses the 30 days: a purge at app start deletes older items. Complete removal of every Windows application is not promised.
## Initial contracts

Domain InstallationIdentity records MSI/Win32/MSIX identity, user/machine scope and optional registry view. InstalledApplication carries discovered display metadata and provenance, without executing a command. OwnershipBasis distinguishes Unknown/NameSimilarity/PublisherMatch from InstallationManifest/InstallationLog/InstallerComponent/ExactPackageIdentity. LeftoverCandidate default selection requires confirmed confidence plus a strong ownership basis, and rejects shared/user-data/reparse targets. Freeform labels never authorize cleanup.

UninstallOutcome classifies Removed/Cancelled/Failed/PendingRestart/Unknown with stable code and restart flag. CleanupReview records the explicit selected candidates, review time and evidence fingerprint for future immediate revalidation. Application IUninstallDiscovery is a read-only port only; no implementation or execution/cleanup adapter exists in foundation. Future invocation must independently validate official registration and package identity; there is no arbitrary executable/path worker request.

## File quarantine (implemented, used by the leftover flow)

`IQuarantine` (Application) and `FileQuarantine` (Infrastructure.Windows) move single files and whole leftover folders out of the way and bring them back. A move deletes nothing.

- The quarantine folder is `%ProgramData%\Winora\quarantine`, created and checked like the journal folder: only administrators can change it or a folder above it, and it is not a link. The app runs as administrator, so a manifest there can be trusted to name the original place of an item. If the folder fails the check, nothing is moved, restored or listed.

- Scan phase: `Inspect` returns the canonical path, the volume serial, the file index, the size and the SHA-256 of a file.
- Move phase: `Move` opens the file again without following reparse points and requires that the final path of the handle equals the canonical path (so no parent folder is a junction or a symbolic link), that it is a regular file with exactly one link, and that the volume, file index, size and hash equal the evidence. Then it renames the file through the handle into the quarantine folder, which must be a plain folder on the same volume. The manifest (original path, fingerprint, hash, time) is written first.
- Refusals carry a stable reason: not found, reparse point, not a regular file, hard-linked, path indirection, identity changed, content changed, too large (over 512 MiB), quota (over 2 GiB in total), locked, access denied, different volume, destination exists, manifest invalid.
- Restore checks the quarantined file against the manifest, requires the original folder to be a plain folder, and never replaces an existing file.
- Folders (`IFolderQuarantine.MoveFolder`): the folder is opened without following a reparse point and held open, so nobody can rename or swap it meanwhile; its final path must be the requested one. Everything inside is walked again: one link or junction anywhere inside, more than 20,000 entries or more than 32 levels, and nothing moves. A drive root child, the quarantine folder itself and a folder that holds it are refused. The manifest (original path, program name, folder identity, size, file count, time) is written first, then the folder is renamed by its handle into the quarantine folder on the same volume. A folder is never copied, so it has no size limit; it does not count against the 2 GiB limit of single files. A folder with a file in use cannot be renamed and stays where it is.
- Folder restore checks the folder identity against the manifest, refuses when anything (file or folder) now has the original name, refuses when the parent folder is gone (Winora does not create it), and renames the folder back by its handle. It never follows a link: the content is not walked, only renamed.
- Delete (the Quarantine tab, after a confirmation) removes the content and the manifest of one entry. The delete is done by handle: the quarantine folder is held open and must be a plain folder whose final path is the folder itself, and each file is opened without following links and deleted through its handle only when its final path is the expected one. A link in place of the folder or a file is refused and left alone; a hard link loses only its name in the quarantine folder. A folder entry is deleted depth first, each entry through its own handle; a link or junction found inside is removed as a link and its target is never entered. A read-only entry has its attribute cleared through the same handle first.
- Restore goes only to a place under the program folders, ProgramData or the profile of the signed-in user (`QuarantineActions`), the same places the leftover scan looks in.
- Purge: items older than 30 days (`LeftoverService.RetentionDays`) are deleted for good once at app start, off the UI thread. Each one is journaled as a purge.

## Leftover scan by ownership evidence (implemented core, no evidence source yet)

This scan of single files by ownership claims is separate from the folder scan of the Apps page below, which is in use.


`LeftoverScanner` (Application) turns the claims of an `IOwnershipEvidenceSource` into `LeftoverCandidate` records. It changes nothing; it only reads and hashes files through `IQuarantine.Inspect`.

- A claim reaches Confirmed only with a strong basis (installation manifest, install log, installer component, exact package identity), a non-empty provenance, a path in a cleanable place and a file that is still a plain regular file whose evidence could be read.
- `LeftoverPathPolicy` classifies each path: system folders and the roots themselves are protected and never inspected; folders named Common Files or Microsoft Shared and the install folders of other registered applications are shared; user profile paths outside the local application data folder are user data; a path outside the known install roots is recognized only inside the recorded install folder, and not when that folder is itself a protected root.
- Malformed paths are refused before any file access: relative, parent or current-folder segments, UNC and device prefixes, alternate streams, trailing dots or spaces, control characters, over 1024 characters.
- At most 5000 claims per scan. Duplicates are reported once. `Fingerprint` hashes the evidence of a reviewed set for `CleanupReview`.
- Not done: a real evidence source, folder handling, a command and a window.

## Disk usage and free up space (implemented)

Decision DEC-IW-020 adds two features to the Cleanup page. This section replaces "no automatic deletion in foundation" for the listed cache groups only; everything else keeps the quarantine rules above.

- Disk usage is a read-only size scan (`DiskScanner`). It never follows reparse points (junctions, symbolic links, mount points) and counts them, counts folders it cannot open, keeps the largest 256 files of each folder and one aggregate with exact totals for the rest, and stops promptly on cancel. Sizes are logical file sizes, not allocated clusters, and a hard-linked file counts at each name. The treemap is a nested squarified layout (area proportional to size, folders as frames, files colored by type, at most 6000 cells, the rest merged into a "smaller items" cell per folder); the list beside it holds the same items and is the keyboard and screen reader path.
- Free up space works on a fixed catalog of user-level cache folders, resolved from the signed-in user's known folders: the user temp folder, the thumbnail and icon database files in the Explorer folder, temporary internet files, the DirectX shader cache, the per-user Windows Error Reporting store and the crash dump folder. A root is accepted only if it is deep enough not to be a drive, is not or does not contain a system, program, profile or application data folder, and is either inside the local application data folder or a temp folder named like one outside the profile's own folders.
- Age rule: the temp folders, the web cache, error reports, memory dumps and update files keep a file when the newest of its write, access and creation times is inside the limit. The page offers 7 days (the default at every start, as in Windows Disk Cleanup), 1 day, or any age; changing it scans again. The scan also reports the count and size of the files it kept for their age. With any age the page and the confirmation warn to close programs first; the removal by handle (below) still skips files that a program has locked.
- A scan lists files and changes nothing. The user sees the groups with sizes and counts, ticks what to remove and confirms once; the confirmation says that the removal is permanent, that files a program has locked are skipped and that open files a program lets others delete (browser caches) can still be removed.
- Before the first removal of a run the intent is written to an append-only journal in the application data folder and flushed to disk; the result is written after the run. A begin line without a result is shown as an interrupted run. If the intent cannot be written, nothing is removed.
- Each file is removed by open handle (`HandleFileRemover`): opened without following links, final path equal to the requested path, regular file with one link, size and last write time equal to the scan, all times older than the age limit, then deleted through a disposition on the handle with a check that the file is not mapped as a program image. A file another program has open cannot be opened for deletion and is skipped. Folders are removed only when empty, deepest first, never a location root.
- The Desktop app runs as administrator (DEC-IW-021). Then the catalog adds exact system locations: the Windows and system temp folders, the Windows Update download folder, the Delivery Optimization cache, the Minidump folder and MEMORY.DMP (the Windows folder only for that single file name, never recursively) and the machine-wide error report store. These never pass through the generic root guard, which refuses every folder inside the Windows folder; a system root is accepted only when it equals one of these entries exactly. Links and hard links inside them are refused by the remover, so a link planted by an unprivileged user in a folder that every user can write to cannot lead the cleanup elsewhere.
- The Recycle Bin is read with SHQueryRecycleBin and emptied with SHEmptyRecycleBin (all drives, no shell dialog); its items cannot be listed or restored. Browser caches are the Cache, Code Cache and GPUCache folders of the Default and numbered profiles of Edge, Chrome and Brave and the cache2 folder of each Firefox profile; cookies, history and passwords are in other folders and are never listed.
- Not in scope: size on disk, scheduled cleanup, and the elevated machine-change channel (it refuses an elevated client).

## Removing programs (implemented, Apps page)

The Apps page removes installed programs. It removes the program; afterwards it offers a leftover scan (next section). It offers no restore point and it cannot undo a removal.

- Desktop programs come from the uninstall registration. A Windows Installer product runs `msiexec.exe /x {code} /qn /norestart` from the System32 folder. This plan is used only when the registration has `WindowsInstaller=1`, its key name is the product code itself, and Windows Installer reports that product as installed for all users; an `msiexec` command in any other registration is refused, so one key cannot remove another product. Other programs run the quiet command they registered; a registration made by Inno Setup (key name ends in `_is1`) gets the silent switches of that installer; a program with only a normal command opens its own uninstaller window; a program with no command is locked. Store packages are removed for all users through the package API, with the same rules and record as the Preinstalled apps page.
- Programs registered for the current user only (HKCU) are removed as that user, never as administrator: any program of the user can write such a registration. The launcher hands the command to the desktop shell of the signed-in user (the documented ShellWindows and `IShellDispatch2.ShellExecute` route through File Explorer), so the uninstaller gets Explorer's token and environment, as when Windows Settings removes it. The shell is used only when its process is `explorer.exe` of the Windows folder, runs as the same account as the app and is not elevated; after an over-the-shoulder elevation (another account) or with an elevated Explorer, the row stays locked and points to Windows Settings. The command must still name an existing `.exe` on a local drive and no command interpreter or loader. The review and the details say that it runs as the user. The started program is followed by its image path, account and start time; when it cannot be followed, the registration read back decides, and a program still registered gets a plain reason. The result is recorded like any other removal.
- Locked rows (never offered): programs registered for the current user only when the desktop shell of this account is not available (see above), system components and programs inside the Windows folder, programs that say they cannot be removed, Winora itself (only the product names of its own installers, "Winora" and "Winora (all users)", with their publisher "Winora project", or a registration whose install folder is the folder the app runs from; another program whose name starts with "Winora" is not locked for that), shared runtimes (Visual C++, .NET, Edge and WebView2), hardware drivers, programs without a removal command, and Store packages that are protected, owned by the system or needed by other apps. The same checks run again when the removal starts.
- One reviewed launcher starts the command. It runs only a machine-scope registration. The main rule is an allow rule by place: the `.exe` must be inside the install folder that the registration names (not a drive root and not the Windows folder or a folder above it), or inside the Windows Installer `Package Cache` folder with a valid signature. A registration with no InstallLocation at all may still run a file in a folder below `%ProgramFiles%` or `%ProgramFiles(x86)%` (not directly in the root), but only when that root, every folder from it down to the file and the file itself can be changed only by SYSTEM, Administrators or TrustedInstaller (owner and every write right read from the ACL); no signature replaces that check, and otherwise the row stays locked with the reason "outside the program folder". A System32 tool is refused whatever its signature. It also accepts only an existing `.exe` by a full local path, never a command interpreter, script host or loader, and never a path with a colon after the drive letter (an alternate data stream). The file itself, its folder and every folder above it up to the drive root must be changeable only by administrators; the file's own owner and ACL are read from the open handle that stays open until the start. A valid signature does not replace this: the uninstaller runs with administrator rights and loads files from its own folder, so a folder that others can change is refused with the reason "untrusted". Files in the `Package Cache` folder and tools in the Windows folder need a valid signature in addition. A row whose command breaks these rules is shown as locked with the reason. There is no shell. Variables such as `%ProgramFiles%` in a registration are expanded with machine values only, never with the user's own. The program does not inherit the environment of the app, which holds the user's own variables. It gets a fixed set: machine values only, a search path inside the Windows folder, the profile folders of the account, and TEMP and TMP in a new folder under `%ProgramData%\Winora\temp` that only administrators can change. Nothing starts if that folder cannot be made. At each start of the app, the folders there that were created more than three days ago are removed (only when `%ProgramData%\Winora\temp` is admin-only; links are never followed, and every entry is removed through the handle remover of the cleanup). It never ends an uninstaller; a time limit or a stop only stops waiting. The time limit follows the Settings choice "Wait for slow tools" (20 to 60 minutes for a quiet uninstaller, 60 to 180 minutes for one with its own window, see [tools.md](tools.md)). A removal whose wait reached the limit is recorded as "still running", never as failed, and the Apps page asks to check again later.
- Order: read the registration again, check protection and administrator rights, write the intent to the journal (nothing starts if that fails), run, read the registration back, write the result. A program counts as removed only when its registration is gone. A restart request is shown. Each program has its own result and reason.
- Not verified on a real PC: see the verification log.

## Leftover folders after a removal (implemented, Apps page and Quarantine tab)

After a desktop program was removed (Removed or Removed, restart needed), its result line on the Apps page has a Find leftovers button. Store apps get none: Windows manages their folders.

- Where it looks (`LeftoverFolderScanner`), and nowhere else: the install folder the registration recorded, if it still exists and is under a program folder, ProgramData or the profile; and in ProgramData, in the Roaming AppData and in the Local AppData of the signed-in user, a folder named exactly for the program, alone or inside a folder named exactly for the publisher. Names are compared whole, ignoring case, as the display name and as the display name without a version number, an architecture tag (x64, 64-bit and similar) or a bracketed part. A publisher name is also tried without a company suffix (Inc, Ltd, GmbH and similar). There is no fuzzy match.
- What it never offers: a name shorter than 3 letters, a generic name (Microsoft, Windows, Common Files, Packages, Temp, Update, Cache and others) or a name that starts with Microsoft or Windows; a name that another installed program also maps to (the scan then makes no name match at all); a publisher folder on its own; the Windows folder and anything in it; the roots themselves (program folders, ProgramData, the profile, AppData, Local, Roaming, LocalLow, Local\Programs, Temp); profile folders outside AppData (Documents, Desktop and others); Common Files, Microsoft Shared, WindowsApps, Package Cache and Packages; the install folder of another program, a folder inside one or a folder that holds one; a folder that is a link or junction or has one above it; a folder with a link or junction inside; a folder with more than 20,000 entries; an install folder outside the known places (another drive, `C:\Tools`). Registry keys are not scanned.
- The review is the shared confirmation dialog with a box per folder, its place, size and file count. The install folder and ProgramData folders start ticked; AppData folders start unticked, because they can hold the person's own settings. The primary button needs one ticked box. Cancel moves nothing.
- Confirm moves each ticked folder into quarantine (above) with the program name and original path. Nothing is deleted at this step. A folder that changed since the scan (now holds a link, is in use, is gone) is refused and stays; the result line says how many moved and the first reason.
- Every move, restore, delete and purge is written to `%ProgramData%\Winora\journals\quarantine-journal.jsonl` before it touches the disk (a begin line, flushed), with an end line after it. A begin without an end shows as interrupted. The History page shows these under Cleanup; the Quarantine tab shows them in its change history block. None is undone from History: a moved item is restored on the Quarantine tab.
- The Quarantine tab lists each item with its name, original folder, program, size, file count and date; the details add the date it will be deleted for good. Restore and Delete work per row; Empty quarantine deletes all after one confirmation. An empty tab shows the shared empty state, which explains where items come from.
- Defaults chosen for owner review: 30 days before the purge; install folder and ProgramData ticked, AppData unticked; the limits of 20,000 entries and 32 levels; the list of generic names.
- Not verified on a real PC: see the verification log.
