Status note: the desktop app now makes real changes with administrator rights (see technical-docs/product.md and architecture.md); the M4a rules below are the safety rules for agents and tests on the development host and still apply in full. FND-001 and M0-M3 (done) delivered the hardened engine, the Windows 11 shell, read-only discovery, 14 real HKCU settings, diagnostics and unsigned packaging. Current scope (owner-delegated, see technical-docs/roadmap.md): M4 privilege foundation, in two phases: (1) security design and review (done): technical-docs/protocol.md (SEC-001), technical-docs/trust.md (SEC-002), an unpublished design note, ADRs, abuse-case table, test lists; (2) now, milestone M4a per technical-docs/m4-implementation-plan.md: implement the protocol framing/crypto, pipe server/client, trust checks and a launcher with tests that run ONLY unelevated, against fakes or an unelevated test worker whose handler set is empty or test-only. Elevation code may be WRITTEN but must never be EXECUTED on the development host: no UAC launch, no runas, no admin tokens, no service or HKLM access; a production worker with no registered handlers must reject every request with worker.unimplemented. HARD SAFETY RULES for M2-M4 and every agent: (1) tests, screenshots, smoke runs and agent experiments must NEVER write the development host's real HKCU settings; every test that touches the registry uses the sandbox root (HKCU\Software\WinoraTests\<guid>, deleted on dispose) and every Desktop/CLI test uses fakes or that sandbox; (2) the production registry adapter only writes targets that are in the authored catalog allowlist, never arbitrary paths, and there is no generic write endpoint; (3) no HKLM, services, scheduled-task changes (the only exception: tests that create, change and delete a task of their own, as the current user, under a folder named WinoraTest-<guid>, and the Scheduled Tasks page when the owner runs the shipped app), deletion of files, uninstallers, arbitrary process starts/kills, power changes or elevation; the ONLY permitted shell actions (owner-approved) are the fixed IShellRefresh kinds, a WM_SETTINGCHANGE broadcast and a graceful Explorer restart that verifies the taskbar returns, which the product performs only after a reviewed and confirmed apply so settings genuinely take effect, and which tests, screenshots and agents must never run against the real shell (use a fake IShellRefresh); Uninstall exception (owner request 2026-10-18, technical-docs/uninstall.md): the Apps page may start the removal command that an installed program registered for itself, through the one launcher file src/Winora.Infrastructure.Windows/Uninstall/RegisteredUninstallLauncher.cs, only after a reviewed and confirmed action by the owner running the shipped app; tests, screenshots and agents must never run an uninstaller (fakes only). Fixed process list (owner-approved): the Tools page may start only the programs of one closed enum, in one reviewed source file, with absolute System32 paths, fixed arguments, no shell and no free text (technical-docs/tools.md), after a reviewed and confirmed action by the owner running the shipped app. Tests, screenshots and agents must never run those repair programs; the runner's own tests start only a harmless System32 program through its test seam. (4) read-only discovery from M1 stays read-only. Only the owner running the shipped app by hand may change their real settings. M4 worker exception (ADR-015, an unpublished design note D-03): the elevated worker executable is a composition root WITHOUT a DI container or logging framework, referencing only Winora.Elevation.Protocol and Winora.Elevation.Windows; in production it registers an empty handler set and rejects every request with worker.unimplemented. Test-only inputs (--sandbox-root, --database, WINORA_DATA_DIR, WINORA_NO_LOG) are not compiled into, and are ignored by, every machine-scope or elevated code path. No script, test, CI step or documented procedure may execute Winora.Worker.exe or Winora.Worker.dll (the only exception is the VM kit under tests/vm, which refuses to run without WINORA_VM_TESTS=1 and the VM marker file). Use temporary directories for tests. Ordinary build outputs and application-owned preferences/journals are allowed.

Preserve independent implementation: Winora is an independent implementation, and behavior evidence for other tools is kept outside this repository. Never copy source, XAML, assets, feature identifiers, curated service tables, power files or descriptions. Write original requirement IDs and language. Preserve GPL-3.0-only SPDX headers and third-party notices.

Domain is platform neutral. Application references Domain only. Windows and Persistence adapters reference Application/Domain. Desktop, CLI and Worker are composition roots. Worker command DTOs belong to Domain and contain no arbitrary targets or commands. No generic execution endpoint. Unimplemented requests must fail explicitly.

Follow technical-docs/operations.md state and durability invariants. Persist before-state and intent before any mutation. Never overwrite external changes during rollback. Do not call unsupported or unimplemented behavior successful. Do not claim UI, Windows integration or release readiness without evidence.

Use .resx for user-facing text, stable codes for persisted outcomes, DI and logging at composition roots, pinned central package versions. Keep changes in the assigned task scope; no unrelated refactors or empty feature implementations. Record implementation status, coverage, acceptance evidence and limits in technical-docs/verification.md and technical-docs/backlog.md.

Documentation is part of the work: in the same change set as any behavior, contract, security or operational change, update the affected documents under technical-docs/ (start from technical-docs/README.md), keep the index and cross-references current, and mark claims that cannot be verified as unverified. Nothing important may live only in a conversation.

When several contributors work concurrently, assign disjoint ownership; do not revert others' edits. All contributors read these governing files. Missing documents must be written and reviewed before dependent implementation.
